Un cambio está hecho cuando se puede demostrar

La skill go-testing-and-verification elige la capa de prueba que demuestra el comportamiento con el menor coste: unitaria para la lógica, tabla para los mismos caminos, golden para el formato y extremo a extremo para el contrato del binario. Después ejecuta la puerta gofmt, build, test, vet y, cuando aplica, race y lint, con la salida real delante.

Qué hace

Elige la prueba que demuestra el comportamiento con el menor coste y cierra el cambio con la salida real de la puerta. La confianza se mide por lo que se puede reproducir, no por un porcentaje.

SituaciónQué hace la skill
Hay que escribir o revisar pruebas.Elige la capa más pequeña que demuestra el comportamiento: unitaria, tabla, golden, extremo a extremo o integración.
Hay que fijar el formato de una CLI.Usa golden files deterministas, normaliza el entorno y actualiza solo con una flag explícita, revisando el diff.
Hay que probar el binario.Lo construye una vez y comprueba por separado stdout, stderr y código de salida, sin asumir TTY.
Un defecto acaba de corregirse.Exige primero una prueba que falle por la causa y luego la corrección; la prueba queda como regresión.
Hay que declarar un cambio terminado.Ejecuta la puerta y muestra los comandos con su resultado; lo no disponible se declara, no se omite.
Una prueba falla de forma intermitente.No la reintenta hasta que pase: elimina la fuente de no determinismo o la declara como defecto.

Lo que no hace. No diseña la CLI, no fija la taxonomía de errores, no impone estilo y no persigue benchmarks de rendimiento. Prueba el contrato que esas skills definen.

La capa la decide el comportamiento. Si el requisito es «el comando devuelve 4 sin --yes», una prueba de función pura no lo demuestra. Si el requisito es una transformación, una prueba de extremo a extremo añade coste sin confianza.

3

Cómo se usa

Siete pasos: decidir qué importa, cubrirlo en la capa correcta y demostrarlo con la puerta ejecutada.

paso 1Mapear

Comportamientos observables y riesgos: datos, secretos, cancelación, concurrencia y compatibilidad del contrato.

paso 2Cubrir la lógica pura

Unitarias para ramas, cálculos y validación; tabla cuando todos los casos recorren el mismo camino; errores con errors.Is/errors.As.

paso 3Fijar la salida

Golden files junto al test, normalización de rutas y tiempos, actualización solo con una flag explícita y validación del JSON.

paso 4Probar el binario

Construcción única, exec.CommandContext, stdin controlado y comprobación separada de flujos y código de salida.

paso 5Cubrir errores y límites

Cada code estable, --dry-run sin mutación, secretos fuera de la salida y cancelación sin fugas.

paso 6Ejecutar la puerta

verify-go.py con gofmt, build, test, vet, race y lint cuando aplique.

paso 7Cerrar con evidencia

Qué se verificó, con qué comando y con qué resultado; qué no se pudo verificar y por qué.

¿Qué capa uso para una CLI?

Lógica pura en unitarias; salida estable en golden; contrato del binario en extremo a extremo. La integración se reserva para la frontera real que el contrato cruza, como un fichero o un HTTP local.

¿Tabla o funciones separadas?

Tabla cuando todos los casos comparten el mismo camino y montaje. Si cada caso necesita preparación propia, la tabla oculta la intención y conviene una función por caso.

¿Qué se comprueba en un extremo a extremo?

stdout, stderr y código de salida por separado; además, ayuda, versión, comando y flag desconocidos, JSON válido, --dry-run, falta de --yes y EPIPE.

El golden cambió sin un cambio explicado

No se actualiza: se investiga la regresión. Actualizar el golden para que pase convierte la prueba en una descripción de lo que el código hace, no de lo que debería hacer.

¿La cobertura es un objetivo?

Es una señal, no una meta. No se escriben pruebas triviales para subir el número; se cubren los comportamientos y riesgos que importan.

¿Y si -race no está disponible?

Se declara. No se sustituye por una ejecución normal y se presenta como equivalente. Lo mismo con golangci-lint: se ejecuta si el proyecto ya lo tiene configurado.

6

Preguntas cortas

Lo que se pregunta antes de usar la skill por primera vez.

¿Qué diferencia hay entre una prueba y una comprobación?

La prueba demuestra un comportamiento y queda en el repositorio. La comprobación es la ejecución de la puerta sobre el árbol actual. El cierre necesita las dos: pruebas que cubran el riesgo y comandos que se hayan ejecutado.

¿Se usan bibliotecas de aserciones?

No. t.Errorf con entradas, got y want es suficiente. cmp.Diff se acepta para estructuras complejas, con la dirección (-want +got) en el mensaje.

¿Por qué no time.Sleep para sincronizar?

Porque convierte una carrera en una probabilidad. Se inyecta el reloj, se usan canales o esperas observables, y se elimina la dependencia de la red y del entorno.

¿Qué pasa si una prueba necesita credenciales que no existen?

Se entrega con un fixture o se declara el bloqueo. No se convierte el hueco en «pendiente» ni se finge una ejecución que no ocurrió.

¿La cobertura se incluye en el informe?

Si existe el dato, se muestra como señal. No se usa como objetivo ni como prueba de que el comportamiento está cubierto.

¿El script de la puerta sustituye a los comandos de Go?

Los envuelve para que la puerta sea uniforme y su resultado se pueda citar. Sigue siendo gofmt, go build, go test y go vet lo que se ejecuta debajo.

8

Verificación

La puerta y sus propias pruebas se ejecutan; lo que no se pudo verificar se declara con su motivo.

python3 src/go-testing-and-verification/scripts/verify-go.py --root . --race
python3 src/go-testing-and-verification/scripts/test-verify-go.py
python3 scripts/check-repo.py
CódigoSignificado
0Todas las comprobaciones ejecutadas pasan.
1Alguna comprobación falla; se corrige por categoría, no se silencia.
2Uso inválido o una herramienta requerida no está disponible.

La puerta ejecuta el proyecto y solo debe usarse sobre código confiable o en un contenedor sin privilegios. Una comprobación ausente se informa; no se omite.
