Del problema al PRD con evidencia trazable

La skill prd-cartographer convierte una idea, una investigación o un concepto de producto en un PRD que se puede revisar y auditar. No rellena huecos con lenguaje seguro: separa hecho, decisión, inferencia, hipótesis y desconocido, exige métricas medibles y declara el estado de preparación antes de presentar el documento como listo.

Qué hace

Un PRD deja de servir para decidir cuando afirma cosas que nadie comprobó, mide objetivos con intenciones o convierte una solución propuesta en una necesidad validada.

SituaciónQué hace la skill
Hay una idea o una investigación sin estructura.Inventaría las fuentes, extrae afirmaciones atómicas y decide si hay descubrimiento suficiente para un PRD o para un diagnóstico de preparación.
El problema está descrito como una solución.Separa problema, necesidad y propuesta; describe primero a quién afecta, en qué contexto y con qué coste.
El PRD promete resultados sin forma de medirlos.Exige definición, método, fuente, línea base, objetivo, plazo y umbral de fracaso para cada métrica.
Una persona, una cita o una causa no tienen fuente.Las marca como Hipótesis, Parcial o UNKNOWN y añade la evidencia que las desbloquearía.
El alcance no tiene exclusiones.Obliga a escribir In scope y Out of scope y a comprobar que no se contradicen con los objetivos.
Dos fuentes se contradicen.Expone ambas y pide decisión; no elige la más reciente ni suaviza el conflicto con una redacción ambigua.

Lo que no hace. No escribe la arquitectura ni la especificación técnica, no inventa usuarios ni demanda, y no presenta un PRD como aprobado cuando las decisiones del agente siguen siendo propuestas.

3

Cómo se usa

Un encargo, un procedimiento. El orden no cambia; la profundidad de cada paso se ajusta al tamaño del producto o de la feature.

paso 1Delimitar

Crear, revisar o auditar; producto o feature; audiencia y decisión que habilita el documento.

paso 2Inventariar fuentes

Tipo, procedencia, fecha visible, alcance y limitación de cada fuente. Afirmaciones atómicas, sin mezclar hecho y opinión.

paso 3Decidir si hay PRD

Si falta descubrimiento, se entrega diagnóstico y Problem Statement. Si es parcial, el PRD se marca PARCIAL.

paso 4Fijar problema y concepto

Entorno, afectados, dinámica, síntomas, causas demostradas e hipótesis causales. Después, el Universal Idea Model.

paso 5Redactar

Plantilla de PRD, requisitos trazables, user stories con beneficio y criterios de aceptación observables.

paso 6Revisar coherencia

Contradicciones entre problema, personas, objetivos, funcionalidades, métricas, alcance y dependencias; después, la puerta de calidad.

paso 7Planificar validación

Validaciones de producto, diseño, ingeniería, QA y usuarios; versión, estado, propietario, historial y condiciones que obligan a revisar.

paso 8Cerrar con evidencia

Estado, documento entregado, trazabilidad, contradicciones, decisiones pendientes y validaciones necesarias.

Falta el problema o los usuarios

No se rellena el PRD con categorías genéricas. Se entrega un diagnóstico de preparación con Estado: NO LISTO y el documento de descubrimiento que falta.

Hay evidencia, pero es parcial

El PRD se redacta como PARCIAL. Cada hueco crítico lleva UNKNOWN, Hipótesis o Parcial, con la pregunta o la prueba que lo desbloquearía.

Una métrica no tiene línea base

Se declara lo que falta. Una métrica sin línea base puede seguir siendo válida como propuesta de medición, pero no permite afirmar que se ha alcanzado un objetivo.

Dos fuentes se contradicen

Se determina qué fuente tiene responsabilidad sobre esa afirmación. Si ambas la reclaman, se exponen las dos y se pide decisión; el PRD no se declara LISTO.

El encargo mezcla producto y técnica

Se separa el requisito de producto y la decisión técnica. La segunda queda como dependencia, restricción o pregunta abierta, no como instrucción de implementación.

Cómo se cierra

Con Estado de preparación, Documento entregado, Fuentes inventariadas, Afirmaciones críticas y trazabilidad, Contradicciones y UNKNOWN, Decisiones pendientes, Validaciones necesarias y Veredicto de la puerta de calidad. Un campo sin evidencia es el hallazgo.

6

Preguntas cortas

Lo que se pregunta antes de usar la skill por primera vez.

¿Esto sustituye a la documentación técnica?

No. El PRD define qué se construye, para quién y cómo se medirá el resultado. La arquitectura, el diseño técnico, la API y los runbooks tienen sus propios artefactos y su propia fuente de verdad.

¿Se puede escribir un PRD con una idea y poco más?

Se puede escribir un diagnóstico de preparación y un Problem Statement. Un PRD concluyente exige problema, usuarios y evidencia; sin ellos, el documento sería una propuesta disfrazada de hecho.

¿Qué diferencia hay entre una inferencia y una propuesta?

La inferencia es una conclusión que se extrae de evidencia existente y debe explicar su razonamiento. La propuesta es una decisión que nadie ha adoptado y debe aprobarse o descartarse. Confundirlas convierte una idea en un compromiso.

¿Por qué una métrica necesita línea base?

Sin línea base no se puede saber si el objetivo representa una mejora. Si no existe, se declara UNKNOWN y se define cómo obtenerla antes de evaluar el resultado.

¿Qué significa que un PRD esté «listo para revisión»?

Que no quedan fallos críticos de evidencia, coherencia o medibilidad y que puede circular para revisión humana. No significa que esté aprobado ni que las validaciones con producto, diseño, ingeniería, QA y usuarios hayan terminado.

¿Y si el usuario pide expresamente un PRD completo?

Se entrega lo que la evidencia sostiene y se declara el resto como hueco. Complacer con relleno produce un documento más largo y menos útil; la puerta de calidad no se negocia.

Verificación

El documento se contrasta con la evidencia y la puerta del repositorio se ejecuta; un PRD con una contradicción abierta no se declara terminado.

python3 scripts/check-repo.py
CódigoSignificado
0Estructura, enlaces y recibos sin hallazgos.
distinto de 0Algún hallazgo; se corrige antes de cerrar.

La puerta comprueba estructura y enlaces, no si el requisito es correcto. Las validaciones de producto, diseño, ingeniería, QA y usuarios quedan registradas con su estado en el cierre del PRD.
