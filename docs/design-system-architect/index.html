El sistema se define antes que la pantalla

La skill design-system-architect descubre, define, documenta, gobierna y verifica el sistema visual de un producto. Los agentes pueden diseñar e implementar dentro de él; no pueden cambiar sus decisiones consolidadas sin autorización explícita.

1

Qué hace

Convierte el sistema visual en un contrato legible por agentes y personas. Define identidad, tokens, temas, componentes, patrones, accesibilidad, movimiento y reglas de cambio; después genera el catálogo y comprueba que contrato y artefactos siguen siendo coherentes.

Descubre

Inventaría un proyecto existente sin escribirlo: documentos, tokens DTCG, variables CSS, componentes y dependencias. Separa lo observado de lo documentado, lo inferido y lo desconocido.

Define

Escribe un contrato verificable con tokens en tres niveles cuando el tamaño lo justifica. Los componentes consumen tokens semánticos o de componente; los primitivos no se usan directamente.

Gobierna

Distingue lo protegido, lo configurable y las excepciones autorizadas. Un cambio protegido exige aprobación externa; el agente no puede crear ni modificar esa aprobación.

Verifica

Comprueba estructura, tokens, referencias, ciclos, cambios protegidos, consistencia del catálogo y informes de adaptadores. Separa PASS, FAIL y UNKNOWN.

2

Cuándo se activa

Úsala para

Crear un sistema visual; auditar uno existente; proponer su evolución; generar tokens o contratos de componentes; publicar un catálogo; comprobar que una implementación respeta el sistema aprobado.

No la uses para

Construir pantallas, componentes o recursos gráficos —eso pertenece al contrato de diseño visual de interfaces— ni para sustituir arquitectura, lógica, seguridad o pruebas funcionales. Tampoco inventa un sistema nuevo cuando ya existe uno que debe conservarse.

La diferencia es de propiedad, no de tema: esta skill define el contrato; la de diseño visual lo consume y materializa la interfaz. Si el encargo exige cambiar el sistema, se detiene la implementación y se sigue el flujo de gobernanza.

3

El contrato

design-system.json es un esquema propio (design-system.v1). Los tokens siguen un subconjunto declarado de DTCG 2025.10: $value, $type, grupos, herencia de tipo, alias con {ruta}, $root y $deprecated.

ParteQué declara
identityPropósito y principios. Es la parte que una implementación no puede reinterpretar.
tokens / tokenSourcesTokens embebidos o fuentes DTCG externas. Una sola fuente canónica; duplicar valores es un error.
themesModo por defecto y overrides por modo. Cada override apunta a un token existente.
componentsPropósito, cuándo y cuándo no, variantes, estados y ejemplo. Una variante sin regla de uso no está especificada.
governanceRutas protegidas, parámetros configurables y excepciones declaradas.
catalog / adaptersDónde vive el catálogo y qué informes externos declaran conformidad de componentes.

No se afirma conformidad DTCG completa. No se implementan $extends, JSON Pointer, todos los tipos compuestos ni todas las reglas de la especificación. Los límites están escritos en el contrato y en la referencia del modelo.

4

Gobernanza

El flujo es READ → PROPOSE → APPROVE → APPLY → VERIFY. Los cambios rutinarios compatibles no piden aprobación; los que tocan una decisión consolidada sí.

Protegido

Identidad, tokens consolidados y contratos estables. Cambiar, añadir o eliminar exige una aprobación externa que cubra la ruta.

Configurable

Valores pensados para adaptarse por proyecto o densidad. Se cambian dentro del contrato, con evidencia y sin reescribir la identidad.

Aprobación externa

Se aporta en un archivo aparte con id, path, approved_by, approved_at, source y reason. El agente no lo crea ni lo modifica.

Límite honesto

El validador comprueba el alcance de la aprobación, no su autenticidad. approved_by por sí solo no autoriza nada; la firma o el ticket son la fuente real cuando el proyecto los exige.

5

Catálogo

catalog genera un catálogo estático desde el contrato: fundamentos, tokens, temas, componentes, patrones, restricciones, decisiones, gobernanza y evidencia. Consume los mismos tokens que el producto mediante tokens.css; no crea una segunda paleta ni un segundo componente.

python3 scripts/design_system.py catalog design-system.json --out docs/design-system

El manifiesto guarda las huellas del contrato, de cada fuente DTCG y de cada artefacto generado. Cambiar cualquiera de ellos invalida el catálogo y check lo demuestra. Todo el texto del contrato se escapa; los ejemplos se muestran en un iframe con sandbox.

La composición y la revisión visual del catálogo no son de esta skill. Se ejecutan con el contrato de calidad visual del proyecto, sin cambiar el contenido ni los tokens.

7

Cómo se usa

# Inventariar un proyecto existente sin escribir nada
python3 scripts/design_system.py discover . --json

# Comprobar el contrato
python3 scripts/design_system.py check design-system.json

# Generar el catálogo
python3 scripts/design_system.py catalog design-system.json --out docs/design-system

# Puerta de un cambio protegido
python3 scripts/design_system.py gate design-system.json \
  --baseline .design-system.baseline.json \
  --approvals approvals.json
CódigoSignificado
0PASS: todas las comprobaciones ejecutadas pasaron.
1FAIL: hay un incumplimiento demostrado.
2UNKNOWN: una comprobación necesaria no se pudo ejecutar.
3Error de uso o de entrada/salida.

9

Preguntas cortas

¿Sustituye a la skill de diseño visual?

No. Define el sistema que esa skill consume. La una posee el contrato; la otra, la ejecución y el juicio visual.

¿Es un framework de componentes?

No. Describe valores, contratos y reglas; no impone un stack ni genera una aplicación.

¿Convierte un proyecto existente en uno nuevo?

No. Descubre y conserva lo que existe. Si hay contradicciones, las declara; no las sobrescribe.

¿Una aprobación la puede crear el agente?

No. El archivo de aprobaciones es externo. El validador comprueba su alcance, no su autenticidad; approved_by por sí solo no autoriza.

¿Un PASS demuestra que el diseño se ve bien?

No. Demuestra coherencia estructural. La calidad visual y la accesibilidad completa necesitan inspección renderizada y medición; sin ellas quedan en UNKNOWN.

¿El catálogo es otra implementación?

No. Se genera desde el contrato y consume los mismos tokens. Editar el HTML o el CSS generados rompe la sincronía y check lo detecta.

11

Verificación

La puerta distingue lo que demuestra de lo que solo declara.

ResultadoSignificado
PASSLa comprobación se ejecutó y no encontró incumplimientos.
FAILHay un incumplimiento demostrado: token mal formado, referencia rota, ciclo, cambio protegido sin aprobación, catálogo desincronizado o adaptador que falla.
UNKNOWNLa comprobación no se ejecutó o la evidencia es insuficiente: falta baseline, catálogo, informe o medición. Nunca se redondea a PASS.
 
python3 scripts/design_system.py check design-system.json
python3 scripts/design_system.py gate design-system.json --baseline .design-system.baseline.json --approvals approvals.json

Un PASS estructural no demuestra calidad visual ni conformidad de accesibilidad. Contraste, foco, teclado, reflow y movimiento se miden en el render; sin esa evidencia quedan en UNKNOWN.
