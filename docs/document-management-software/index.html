Documentación de software con fuente de verdad

La skill document-management-software gestiona la documentación de un proyecto de software. No escribe nada antes de leer cómo está el proyecto: cada afirmación sale del código, de los tests, de la configuración o de una decisión explícita, y lo que no tiene fuente se queda como pregunta abierta. Si un dato ya está documentado, lo enlaza; si está mal, lo corrige; crea un documento solo cuando ese conocimiento no tiene dónde vivir.

Qué hace

La documentación deja de ser verdad de tres maneras: afirma cosas que nadie comprobó, repite un dato en dos sitios que después divergen o describe un estado que el código ya abandonó.

SituaciónQué hace la skill
Hay que documentar algo que ya funciona.Lee código, tests y configuración antes de escribir, y copia de ahí los nombres, las rutas, los valores y los comandos.
El mismo dato está en dos documentos.Uno queda como fuente canónica y el otro lo enlaza. Dos representaciones que pueden divergir no se mantienen a mano.
El README describe algo que el código ya no hace.Corrige la afirmación o la marca como histórica con su motivo. No la completa con generalidades.
La guía cita un SHA, una ruta de la máquina de quien escribió o un recuento de ficheros.Lo deja fuera y lo sustituye por el dato estable: la ruta relativa, el comando, la regla. Eso envejece sin aviso y nadie lo actualiza.
Falta un documento.Mira primero si el contenido cabe en uno existente sin degradar su responsabilidad. Crear es la última opción, no la primera.

Lo que no hace. No escribe contenido comercial ni material de marketing, no reescribe tests ni contratos que ya se pueden ejecutar, y no cierra una intervención sin mostrar la comprobación que la respalda.

3

Cómo se usa

Un encargo, un procedimiento. El orden es el mismo; el tamaño del encargo cambia la profundidad de cada paso.

paso 1Delimitar

Qué se pide —crear, actualizar, auditar o responder—, para quién se escribe y qué fuente responde de cada afirmación.

paso 2Inventariar

Ejecutar el script, asignar a cada documento su responsabilidad y ver qué está cubierto, qué falta y qué está cubierto dos veces.

paso 3Fijar la certeza

Clasificar cada afirmación antes de redactarla: confirmada, inferencia, propuesta, desconocida, contradictoria u obsoleta.

paso 4Elegir la intervención mínima

Una sola acción: nada, corregir, reordenar, deduplicar, ampliar, enlazar o crear.

paso 5Redactar

Con la terminología del proyecto, los valores copiados de la fuente y lo propuesto separado de lo implementado.

paso 6Verificar

Repetir el inventario y contrastar cada afirmación modificada contra su fuente.

paso 7Cerrar con evidencia

Cinco líneas: intervención, artefactos, verificación, afirmaciones sin sustento y pendientes.

python3 scripts/doc-inventory.py --root <directorio> [--glob "*.md"] [--json]

Alcance del inventario. Si la raíz tiene .doc-inventory-ignore, sus patrones son rutas relativas a la raíz y se aplican antes de analizar: a.md solo excluye ese fichero en la raíz y docs/ solo esa carpeta. El informe dice cuántas rutas quedaron fuera.

El script sale con 0

Inventario completo sin hallazgos. Esa lista es la línea base antes de tocar nada.

El script sale con 3

Hay hallazgos: enlaces relativos rotos, documentos sin título, documentos vacíos, encabezados repetidos entre documentos o referencias vivas escritas como documentación. Es una salida esperada. Para cada uno se decide si se corrige en este encargo o se reporta con evidencia.

El script sale con 2

Error de uso: la ruta no existe, no es un directorio o el patrón incluye separadores. Se corrige el argumento; no se sustituye el script por una revisión a ojo.

Falta una fuente imprescindible

Se formula una sola pregunta concreta y se detiene el trabajo ahí. No se rellena el hueco con una suposición plausible.

Dos fuentes se contradicen

Se exponen las dos y se pide decisión. Si la documentación es la especificación vigente, a veces lo que hay que arreglar es el software, no el texto.

Cómo se cierra

Intervención, Artefactos, Verificación con su código de salida, Afirmaciones no sustentadas y Pendiente. Un campo que no se puede rellenar con evidencia no se disfraza: ese campo es el hallazgo.

6

Preguntas cortas

Lo que casi todo el mundo pregunta en la primera conversación.

¿Qué diferencia hay entre una inferencia y una propuesta?

La inferencia es una conclusión sacada de evidencia que ya existe: se confirma o se baja de grado. La propuesta es un diseño que nadie ha adoptado todavía: se aprueba o se descarta. Confundirlas convierte una idea en un hecho, y eso es lo que luego alguien ejecuta en producción.

¿Se puede pedir que documente sin leer el código?

Se puede, y sale otra cosa: propuestas y huecos declarados, no el estado implementado. Si lo que se quiere es describir el comportamiento actual, leer las fuentes es parte del trabajo, no un extra.

¿Por qué no basta el código como documentación?

El código dice cómo está, pero no la intención, las restricciones ni por qué se descartaron las alternativas. Y quien opera una incidencia no lee el código para saber qué hacer.

¿Y si el proyecto ya tiene su propia estructura documental?

Se respeta tal cual, aunque a la skill le parecería mejor otra. Proponer un cambio de convención es un encargo aparte y explícito. Esta misma página se rige por esa regla: es la convención de SKILLS-AGP, no una norma de la skill.

¿Sirve para documentar una dependencia externa?

Sí, con límites. Se prioriza la documentación oficial y se identifica la versión consultada; después se escribe cómo y por qué la usa este proyecto. Copiar su documentación entera crea una segunda fuente que nadie va a mantener.

¿El cierre es obligatorio aunque el cambio sea de una línea?

Sí, con tamaño proporcional: cinco líneas donde «Artefactos» y «Verificación» pueden ser un comando o «ninguno». Lo que no se admite es declarar terminado algo sin ninguna comprobación detrás.

8

Verificación

El inventario y la puerta del repositorio se ejecutan; un documento sin H1, con un enlace roto o con una referencia viva no se declara terminado.

python3 src/document-management-software/scripts/doc-inventory.py --root .
python3 src/document-management-software/scripts/test-doc-inventory.py
python3 scripts/check-repo.py
CódigoSignificado
0Sin hallazgos; el inventario y las pruebas terminaron.
3Hallazgos: enlace roto, documento sin H1, vacío, encabezado repetido o referencia viva.
2Error de uso o de entorno; el inventario no llegó a leer los documentos.

El inventario comprueba estructura y enlaces, no la verdad de lo afirmado. La fuente de cada afirmación la contrasta quien escribe el documento.
