Qué hace

Mide la confianza en el comportamiento que importa; un porcentaje de cobertura no la demuestra. En TypeScript hay dos verdades que deben coincidir: lo que el compilador acepta y lo que el programa recibe en runtime.

SituaciónQué hace la skill
Entra un dato de HTTP, formulario, fichero o process.env.Lo valida en la frontera con un esquema y deriva el tipo con z.infer.
Un handler recibe una petición.Usa safeParse, traduce el error a la forma que consume el receptor y no devuelve el input completo.
Hay lógica con ramas, cálculos o transformaciones.Escribe pruebas unitarias o de tabla, con casos válidos, inválidos y de límite.
El contrato cruza una frontera real.Añade integración con servidor local, directorio temporal y dependencias inyectadas.
Hay que probar una CLI.Construye el binario una vez y comprueba stdout, stderr y código de salida por separado.
Hay que declarar un cambio terminado.Ejecuta la puerta con verify-ts.py y copia el informe con la salida real.

Lo que no hace. No diseña tipos, módulos, dependencias ni la arquitectura de la CLI. Esa materia es de typescript-idiomatic-style; aquí solo se demuestra que lo construido se comporta como dice.

3

Cómo se usa

Seis pasos. El mapa decide qué merece prueba; los siguientes la escriben y la ejecutan.

paso 1Mapear comportamientos y riesgos

Lo que se observa, las fronteras por las que entra dato no confiable y los riesgos: datos, secretos, cancelación, contrato.

paso 2Validar las fronteras

Un esquema por contrato externo, tipos derivados, safeParse en handlers y parse en configuración. El servidor revalida.

paso 3Cubrir la lógica

Pruebas de esquema con válidos, inválidos y límites; unitarias para lógica pura; integración con dependencias reales sustituidas.

paso 4Probar la CLI

Binario construido una vez, spawn/execFile, stdout y stderr separados, ayuda, versión, errores, JSON, cancelación y --dry-run.

paso 5Ejecutar la puerta

verify-ts.py con las comprobaciones que el proyecto soporte. Si falla, se corrige por categoría; no se silencia.

paso 6Cerrar con evidencia

Copia assets/verification-report.md, rellena con la salida real y declara lo no verificado con su motivo.

¿Zod siempre?

Se usa el validador que el proyecto ya tenga. Si hay que elegir, Zod 4; no se añade un segundo validador ni dos versiones mayores. El contrato de frontera importa más que la biblioteca.

¿parse o safeParse?

safeParse cuando el dato viene de un usuario y el fallo es una respuesta esperada. parse cuando el dato inválido es un bug o un arranque inválido. Lo asíncrono exige parseAsync o safeParseAsync.

¿Qué cubre una prueba de esquema?

Entradas válidas, inválidas y de límite: cadena vacía, null, ausente, tipo incorrecto, clave extra, coerción y número fuera de rango. Se comprueba la forma del error, no el texto volátil.

¿Cómo se prueba la CLI?

Se construye el binario una vez y se ejecuta con argumentos explícitos y stdin controlado. Se comprueban por separado stdout, stderr y código de salida; no se asume TTY.

¿Y si una prueba es inestable?

No se reintenta hasta que pase. Se elimina la fuente de no determinismo (reloj, red, orden, rutas) o se declara como defecto.

¿La cobertura es un objetivo?

No. Es una señal. Escribir pruebas triviales para subir el número no aumenta la confianza en el comportamiento.

6

Preguntas cortas

Lo que se pregunta antes de usar la skill por primera vez.

¿Hay que llegar a un porcentaje de cobertura?

No. La cobertura es una señal, no un objetivo. Cada prueba debe aumentar la confianza en un comportamiento observable; si no, sobra.

¿Se pueden usar mocks?

Sí, en la frontera externa. No se mockea el módulo que se está probando, y un doble debe poder fallar como fallaría el real. Preferir una dependencia inyectada a un mock global.

¿Qué pasa si el proyecto no tiene lint?

No se añade solo para cumplir la puerta. Se ejecutan las comprobaciones disponibles y se declara la ausencia en el informe.

¿Y si falta tsc local?

Se declara el bloqueo. No se ejecuta un npx que descargue una versión distinta de la que usa el proyecto.

¿Cómo se prueba la cancelación?

Enviando la señal o un stdin que simule la interrupción, y comprobando que no queda un proceso hijo ni un archivo parcial.

¿Cuándo está terminado un cambio?

Cuando la puerta se ejecutó, el informe recoge los comandos y su resultado, y lo no verificado se declara con su motivo. Un fallo conocido no se convierte en pendiente.

8

Verificación

La puerta y sus propias pruebas se ejecutan; lo que no se pudo verificar se declara con su motivo.

python3 src/typescript-testing-and-verification/scripts/verify-ts.py --root . --test --lint --build
python3 src/typescript-testing-and-verification/scripts/test-verify-ts.py
python3 scripts/check-repo.py
CódigoSignificado
0Todas las comprobaciones ejecutadas pasan.
1Alguna comprobación falla; se corrige por categoría, no se silencia.
2Uso inválido o una herramienta requerida no está disponible.

La puerta ejecuta el proyecto y solo debe usarse sobre código confiable o en un contenedor sin privilegios. Una comprobación ausente se informa; no se omite.
