Una CLI que un agente puede predecir

La skill go-cli-ai-first fija el contrato de una CLI en Go antes de implementarla: comandos y flags estables, stdout para el resultado y stderr para el diagnóstico, un sobre JSON de éxito y de error, códigos de salida acotados y un plan que se puede leer antes de que nada cambie. El consumidor principal es un agente que ejecuta, lee y decide el siguiente paso; si tiene que adivinar, la CLI no está terminada.

1

Qué hace

Convierte la interfaz de una CLI en un contrato que un agente puede descubrir, ejecutar y comprobar sin leer el código. La comodidad humana no se sacrifica: se subordina a la previsibilidad máquina.

SituaciónQué hace la skill
Hay que crear una CLI desde cero.Delimita binario, dominio y consumidores reales, y escribe una ficha por comando antes de implementar.
Hay que añadir o cambiar un comando, un flag o la salida.Exige el contrato actualizado y decide si el cambio es compatible o incompatible, con versión y migración.
Un comando borra, sobrescribe o publica.Le exige --dry-run con el plan en stdout y --yes para ejecutar; sin ellos no muta nada.
El consumidor es un agente o un script.Separa resultado y diagnóstico, impone el sobre JSON y fija los códigos de salida como parte del contrato.
Un comando necesita una decisión y no hay TTY.Falla con error de uso y nombra la flag exacta que falta; no lee stdin a ciegas ni abre un prompt.
Una CLI existente no se puede automatizar con confianza.Audita ayuda, JSON, códigos, idempotencia, límites de salida, cancelación y separación de flujos, y declara lo que falta.

Lo que no hace. No decide el producto, no diseña interfaces gráficas ni APIs HTTP, no impone una arquitectura de microservicios y no sustituye a las skills de estilo, errores o pruebas: remite a ellas para sus reglas.

El contrato escrito va primero. Un comando sin ficha no se implementa. La ficha fija entrada, salida, errores, efectos, idempotencia, seguridad y códigos; si algo no se puede describir ahí, todavía no está listo para codificarse.

3

Cómo se usa

Ocho pasos en orden. La profundidad cambia con el tamaño de la CLI; la presencia de cada paso, no.

paso 1Delimitar

Binario, dominio, consumidores y operaciones. Antes de nombres, se lee el contrato de referencia.

paso 2Escribir el contrato

Una ficha por comando: entrada, salida, error, efecto, idempotencia, --dry-run y --yes.

paso 3Elegir la estructura

main como cableado, run comprobable, dependencias inyectadas y ninguna capa anticipada.

paso 4Implementar la superficie

Ayuda antes que lógica, FlagSet con salida propia, un renderizador de texto y otro JSON.

paso 5Añadir seguridad

Plan de --dry-run, --yes, escritura atómica, changed e idempotencia.

paso 6Resolver el ciclo de vida

signal.NotifyContext en main, timeouts en su frontera y cierre en orden inverso.

paso 7Probar el contrato

Unitarias, golden y extremo a extremo con stdout, stderr y código de salida por separado.

paso 8Cerrar con evidencia

gofmt, build, test, vet y race si hay concurrencia; resultado sin huecos.

¿Qué código de salida devuelvo?

El contrato fija cinco: 0 éxito, 1 fallo de ejecución, 2 error de uso, 3 cancelado y 4 precondición o conflicto. No se inventan códigos por comando, y un fallo parcial por lotes es 1, no 0.

¿Qué pasa sin --yes?

Una operación destructiva muestra el plan y sale con 4. No se ejecuta, no se pregunta por terminal y no se interpreta un prompt interactivo como autorización.

¿Cómo se comporta con --json?

Emite exactamente un documento en stdout: {"ok":true,"command":"...","data":...} o {"ok":false,"error":{"code":"...","message":"...","details":...}}. Los flujos continuos usan JSON Lines y lo declaran.

El consumidor cierra la tubería

EPIPE es una salida normal: el comando termina con 0 y sin ruido. Un error de escritura distinto se trata como fallo de ejecución.

Repetir la operación, ¿falla?

Si el dominio lo permite, es idempotente: mismo estado, éxito y changed:false. Un conflicto real devuelve 4; sobrescribir exige --force explícito.

¿Puedo renombrar un flag?

Renombrar o eliminar un comando, flag, campo JSON o código de salida es un cambio incompatible: exige versión mayor y nota de migración. Añadir es compatible; cambiar en silencio, no.

6

Preguntas cortas

Lo que se pregunta antes de usar la skill por primera vez.

¿Sirve para una CLI con interfaz interactiva?

Sí, con una condición: la interacción es una capa opcional sobre un contrato no interactivo. Si una operación solo se puede expresar con un prompt, se rediseña como plan y apply.

¿Por qué no usar el paquete de flags del proyecto?

Se puede usar. Lo que no se delega es el comportamiento: FlagSet con salida propia, ayuda que sale con 0, flag desconocido con 2 y ningún os.Exit fuera de main. Una biblioteca con convenciones propias se respeta sin romper esas invariantes.

¿Dónde vive el mapeo de errores a códigos?

En un solo punto, cerca de main. El dominio no conoce códigos de proceso. La taxonomía y la envoltura pertenecen a la skill de errores y ciclo de vida.

¿Hay que implementar concurrencia?

Solo si el dominio la necesita. Cuando aparece, se diseña con la skill de errores y ciclo de vida: propietario, terminación, propagación y espera. La CLI se limita a propagar el contexto y a respetar la cancelación.

¿Cómo se limita la salida?

Los listados aceptan --limit con un valor por defecto razonable; los flujos infinitos exigen --follow. Ninguna operación imprime indefinidamente sin control del llamador.

¿Qué hago si el contrato JSON ya existe?

Se respeta y se documentan las diferencias. No se impone el sobre de esta skill sobre un contrato publicado; la compatibilidad con los consumidores manda.
