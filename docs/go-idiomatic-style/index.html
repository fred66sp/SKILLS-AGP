Go que se lee sin reconstruir la intención

La skill go-idiomatic-style escribe y revisa Go idiomático para CLIs y servicios pequeños. Ordena las decisiones por claridad, simplicidad y mantenibilidad; trata gofmt como la fuente del formato, la biblioteca estándar como primera opción y la estructura mínima como punto de partida. No convierte una preferencia estética en una capa nueva.

1

Qué hace

Reduce el coste de leer y cambiar código Go sin sacrificar claridad, seguridad ni capacidad de evolución. La sencillez se demuestra con menos piezas, no con más.

SituaciónQué hace la skill
Hay que escribir código Go nuevo en una CLI o un servicio pequeño.Parte de la estructura mínima, la biblioteca estándar y las convenciones que ya existen en el proyecto.
Hay que refactorizar sin cambiar el comportamiento.Separa la refactorización del cambio funcional y revisa que el diff no mezcle ambos.
Hay que decidir paquetes, nombres o dependencias.Aplica una frase de responsabilidad por paquete, nombres por ámbito y dependencias justificadas por necesidad.
Aparece una interfaz, un genérico o una opción funcional.Exige dos usos reales o una frontera que probar; si no existen, entrega la versión concreta.
Hay que revisar estilo y diseño.Comprueba formato, nombres, flujo con errores primero, semántica de datos e interfaces del consumidor.
Una regla del proyecto choca con el lenguaje.Respeta la convención existente salvo en el formato: gofmt no se negocia.

Lo que no hace. No diseña el contrato de la CLI, no define la estrategia de errores, no introduce concurrencia y no escribe la verificación. Cada una de esas decisiones tiene su propia skill y su propio dueño.

La consistencia gana los empates. Cuando claridad, simplicidad, concisión y mantenibilidad están igualadas, se sigue lo que ya hace el proyecto. La skill no impone un estilo propio sobre un código que funciona y se lee.

3

Cómo se usa

Siete pasos. El primero y el último son de lectura; los de en medio deciden y escriben.

paso 1Inspeccionar

go.mod, paquetes, tests y código vecino. La convención escrita del proyecto prevalece.

paso 2Fijar el mapa de paquetes

Una frase de responsabilidad por paquete; dominio separado de flags y presentación; sin util ni ciclos.

paso 3Nombrar

Paquetes de una palabra, exportados en PascalCase, receptores cortos, constantes en MixedCaps y nombres por ámbito.

paso 4Diseñar

Funciones con una responsabilidad, interfaces pequeñas en el consumidor, retornos concretos y datos con semántica explícita.

paso 5Implementar

Camino normal y guard clauses primero; sin init() con efectos; dependencia nueva con su motivo en el diff.

paso 6Formatear y compilar

go fmt ./..., go vet ./... y go build ./.... Un cambio de estilo que rompe la compilación no es un cambio de estilo.

paso 7Revisar el diff

Sin abstracciones ni dependencias no pedidas, sin reformatear código ajeno, sin mezclar refactorización y comportamiento.

¿Cuándo se justifica una interfaz?

Cuando existe un consumidor real que necesita abstraerse de la implementación. Se declara en su paquete, con los métodos que usa, y el productor devuelve el tipo concreto. Una interfaz sin uso es una capa de más.

¿Por qué no util o helpers?

Porque un nombre que no describe nada atrae código sin relación. Si aparece un cajón, se nombra por el dominio que contiene o se reparte entre los paquetes que lo usan.

¿Puedo añadir una dependencia?

Solo con una necesidad concreta y una revisión de licencia, mantenimiento y superficie de seguridad. Se escribe en el diff por qué la biblioteca estándar no basta. Si no se puede revisar, se declara el bloqueo.

¿Y si el proyecto no usa la estructura de la skill?

Se respeta la del proyecto. La estructura mínima es el punto de partida cuando no hay convención, no una migración obligatoria dentro de un cambio funcional.

¿Qué pasa con panic?

Solo para invariantes imposibles o fallos de inicialización que impiden arrancar, y nunca cruzando una frontera de paquete. Un error esperado se devuelve.

¿La skill arregla la deuda que encuentra?

No la esconde en el mismo diff. Si sustituir una abstracción incorrecta amplía el cambio, se termina la tarea actual y se registra la deuda con su motivo.

6

Preguntas cortas

Lo que se pregunta antes de usar la skill por primera vez.

¿Es una guía de estilo propia?

No. Toma las decisiones del lenguaje y de la comunidad, y las ordena para que una CLI pequeña se mantenga legible. Donde el proyecto ya tiene una regla escrita, manda la del proyecto.

¿Cuántas capas debe tener una CLI?

Las que necesite. Una CLI pequeña puede vivir en un solo paquete; cmd/ e internal/ se añaden cuando existe una necesidad concreta, no por anticipación.

¿Puntero o valor?

Se elige por semántica: mutación, ausencia con nil, tamaño o identidad. No por una intuición sobre la pila o el montón.

¿Se pueden usar genéricos?

Cuando eliminan duplicación real y el tipo se entiende. No como envoltorio preventivo ni para imitar una biblioteca. La misma regla que una interfaz: sin dos usos reales, no existe.

¿Qué hago con un else después de un return?

Se elimina. El flujo normal va sin anidar: errores y casos especiales primero, retorno temprano, caso feliz sin indentación.

¿La skill ejecuta linters?

Ejecuta go fmt, go vet y go build. golangci-lint solo si el proyecto ya lo tiene configurado; no se añade para cumplir esta skill.

8

Verificación

El formato, la compilación y la puerta del repositorio se ejecutan; un cambio de estilo que rompe la compilación no es un cambio de estilo.

gofmt -l .
go vet ./...
go build ./...
python3 scripts/check-repo.py
CódigoSignificado
0Formato, vet y compilación sin hallazgos.
distinto de 0Algún comando falla; se corrige antes de cerrar.

gofmt no se negocia. La puerta no juzga la claridad de los nombres ni la necesidad de una abstracción: eso lo decide la revisión del diff.
