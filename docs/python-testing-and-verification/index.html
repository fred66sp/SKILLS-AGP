Prueba lo que se ejecuta, no lo que imaginas

La skill python-testing-and-verification elige la capa más pequeña que demuestra el comportamiento: función pura, módulo con dobles, proceso ejecutado o integración real. Sustituye red, reloj, entorno y ficheros por recursos controlados, y cierra con una puerta que comprueba sintaxis, formato, lint, tipos y las pruebas del proyecto.

Qué hace

Una sospecha no vale como prueba. Elige la capa y escribe el caso que falla por la causa correcta; la puerta queda lista para otra máquina.

SituaciónQué hace la skill
Hay que probar lógica, cálculos o transformaciones.Escribe casos con unittest o pytest junto al módulo, con parámetros cuando el camino es el mismo.
La operación depende de red, reloj, entorno o ficheros.Dobla la frontera o usa tmp_path y monkeypatch; nunca red real ni sleep.
Entra dato de un fichero, HTTP o una cola.Valida en el punto de entrada y prueba cada rechazo, no solo el camino feliz.
El contrato es una CLI.Ejecuta el proceso con subprocess.run, argumentos y entorno controlados, y comprueba stdout, stderr y código de salida por separado.
Aparece un defecto.Primero la prueba que falla por su causa; después la corrección. La prueba queda como regresión.
Hay que declarar el cambio terminado.Ejecuta verify-python.py y rellena el informe con lo ejecutado y lo que no.
El proyecto ya tiene pytest, unittest o tox.Se usan esos; la skill no los sustituye ni añade un segundo runner.

Lo que no hace. No escribe la implementación, no impone estilo ni decide la estructura del paquete. El lenguaje, los tipos y la CLI son de python-idiomatic-style.

3

Cómo se usa

Siete pasos. El riesgo se mapea antes de escribir, la capa se elige una vez y el cierre se demuestra con comandos.

paso 1Mapear riesgos

Qué observa el usuario, dónde entra dato no confiable, qué se destruye o se filtra y qué cambia a menudo.

paso 2Elegir capa y runner

Función pura, módulo con dobles, proceso ejecutado o integración real. Si hay runner, ese manda.

paso 3Escribir el caso

Una razón para fallar, un mensaje legible y los límites: vacío, cero, None, error de red, timeout.

paso 4Aislar y estabilizar

Dobles o inyección de red, reloj y entorno; tmp_path; limpieza de ficheros y conexiones.

paso 5Probar frontera y proceso

Validación del dato externo y CLI con ayuda, versión, flag inválido, --dry-run y falta de --yes.

paso 6Ejecutar la puerta

verify-python.py con --format, --lint, --types y --test. Una herramienta ausente se informa.

paso 7Cerrar con evidencia

Informe con comandos, resultado y lo no verificado. Sin adjetivos.

¿Necesito instalar pytest?

No si el proyecto usa unittest. La puerta ejecuta pytest cuando ya está instalado en el intérprete y, si no, cae en python -m unittest discover cuando encuentra archivos de prueba.

¿Qué comprueba exactamente verify-python.py?

Sintaxis con compile() en cada .py, sin ejecutar código. Con --format, ruff format --check; con --lint, ruff check; con --types, mypy o pyright; con --test, pytest o unittest. Informa de la versión de Python frente a requires-python.

¿La puerta falla si falta una herramienta?

Solo si la pides. Si se pide --lint y ruff no está, la comprobación falla y lo dice; no descarga nada ni continúa como si hubiera pasado.

¿Cómo se prueba una CLI?

Ejecutando [sys.executable, "-m", "paquete", ...] con subprocess.run, capture_output=True, text=True y un timeout. Los tres canales se comprueban por separado.

¿La cobertura es un objetivo?

Es una señal. Un umbral se acepta si ya existía; no se impone dentro de un cambio funcional ni se escriben pruebas triviales para subirlo.

¿Qué hago con una prueba inestable?

Se corrige la fuente de no determinismo o se elimina con motivo escrito. No se marca como omitida ni se le añade una espera mayor.

6

Preguntas cortas

Lo que se pregunta antes de usar la skill por primera vez.

¿Sustituye a pytest?

No. Si el proyecto lo tiene, se usa; si no, unittest de la biblioteca estándar cubre la capa mínima sin añadir una dependencia.

¿Se puede probar sin red?

Sí: el doble declara estado, cabeceras y cuerpo, y se prueban también el error HTTP, el JSON inválido y el timeout. La integración real se marca y se ejecuta aparte.

¿Qué pasa con la validación de tipos?

La puerta comprueba los tipos con mypy o pyright; el diseño de los tipos pertenece a python-idiomatic-style. Una anotación no sustituye la validación en runtime.

¿Cómo se prueba un servicio externo?

Con un contenedor de versión fijada o un servidor local. Si el servicio no está disponible, el test falla o se omite con una razón visible; nunca pasa en silencio.

¿La puerta necesita pyproject.toml?

No. Solo lo lee para informar de requires-python. La comprobación de sintaxis funciona en una carpeta de scripts sin metadatos.

¿Qué hago si un test falla solo en CI?

Se declara la diferencia —versión de Python, variable de entorno, sistema operativo— y se reproduce. No se reintenta hasta que pase.

Verificación

La puerta y sus propias pruebas se ejecutan; lo que no se pudo verificar se declara con su motivo.

python3 src/python-testing-and-verification/scripts/verify-python.py --root . --format --lint --types --test
python3 src/python-testing-and-verification/scripts/test-verify-python.py
python3 scripts/check-repo.py
CódigoSignificado
0Todas las comprobaciones ejecutadas pasan.
1Alguna comprobación falla; se corrige por categoría, no se silencia.
2Uso inválido o una herramienta requerida no está disponible.

La puerta ejecuta el proyecto y solo debe usarse sobre código confiable o en un contenedor sin privilegios. Una herramienta ausente se informa; no se omite.
