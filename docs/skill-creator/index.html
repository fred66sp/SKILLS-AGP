1

Qué es esta skill

Un procedimiento de autoría, no una guía de estilo. Su resultado es un directorio con una forma concreta: metadatos que pasan un validador, un SKILL.md corto y tres carpetas cuyo contenido se carga justo a tiempo.

La especificación de agentskills.io es la guía y la referencia estricta de este repositorio: la estructura de directorios, los metadatos, la divulgación progresiva y los scripts de cada skill se contrastan contra ella, no contra una convención propia. La skill la aplica junto al principio de divulgación progresiva: el cuerpo principal navega y decide; los detalles viven en ficheros que el agente lee solo cuando la operación concreta los pide. Esa separación es lo que permite que una skill sea estricta sin consumir contexto en cada conversación.

El cerebro: SKILL.md

Frontmatter con name y description, y un procedimiento numerado en imperativo. Es el único fichero que el agente ve antes de disparar la skill y el que decide qué se lee después.

Sus campos y su forma salen de la especificación de agentskills.io, que es la referencia estricta del repositorio.

Se mantiene por debajo de 500 líneas: si crece, el detalle se mueve fuera.

El contexto: tres carpetas

scripts/ para lo determinista, references/ para el contexto plano y assets/ para plantillas y ficheros estáticos. Un solo nivel de profundidad en las tres.

No se cargan solas: el SKILL.md ordena cuándo leer cada una.

El procedimiento, en seis pasos

paso 1Metadatos y validación

Elegir name y description, y ejecutar el validador hasta que salga con código 0.

paso 2Estructura del directorio

Crear la raíz con el nombre validado y las tres carpetas estándar. Sin ficheros para personas.

paso 3Redactar SKILL.md

Partir de la plantilla, escribir en imperativo y mover el contexto voluminoso a references/.

paso 4Scripts deterministas

Convertir en CLI de un solo propósito lo que es frágil o repetitivo, con errores legibles.

paso 5Composición (opcional)

Solo si la skill es compleja: una skill enrutadora que deriva a otras según la condición.

paso 6Validación final

Buscar huecos de alucinación, comprobar rutas relativas y pasar la checklist completa.

Cuándo aplicaCuándo no
Crear directorios de skill nuevos.Documentación general.
Redactar instrucciones procedimentales.Código de librería que no es para un agente.
Optimizar metadatos para que la skill se descubra.Ficheros README.md u otra documentación para personas.

Los disparadores negativos no son cortesía: son parte de la description y son lo que evita que la skill se active en la conversación equivocada.

2

Metadatos: nombre y descripción

El name y la description del frontmatter son los únicos campos que el agente ve antes de disparar la skill. Si no están optimizados para el descubrimiento, la skill es invisible por muy buenas que sean sus instrucciones.

CampoReglaPor qué
nameEntre 1 y 64 caracteres. Solo minúsculas, números y guiones simples: sin guiones consecutivos y sin guion al principio ni al final.Es un identificador, no un título.
nameDebe coincidir exactamente con el nombre del directorio padre: name: angular-testing vive en angular-testing/SKILL.md.El enrutamiento y la ruta tienen que decir lo mismo.
descriptionMáximo 1.024 caracteres.Es el texto que decide si la skill se activa o no.
descriptionEn tercera persona, con disparadores positivos («Use when…») y negativos («Don't use for…»).Los positivos la encienden donde debe; los negativos la apagan donde no.

El mismo campo, mal y bien

# Mal: no dice qué hace, ni cuándo, ni cuándo no
description: React skills.

# Bien: capacidad, disparadores positivos y negativos
description: Creates and builds React components using Tailwind CSS. Use when the
  user wants to update component styles or UI logic. Don't use it for Vue, Svelte,
  or vanilla CSS projects.

La descripción mala se dispara en cualquier conversación o en ninguna. La buena acota el disparo con la misma precisión con la que un buen SKILL.md acota los pasos.

La tercera persona no es un formalismo. El validador trata las palabras de primera y segunda persona como un fallo: una descripción que dice «I help you…» describe una conversación, no una capacidad, y el agente que enruta no está dentro de esa conversación.

3

Validar antes de seguir

El paso 1 no termina con una decisión, termina con un código de salida 0. Mientras el validador falle, no se crea la estructura: se corrige el metadato y se vuelve a ejecutar.

python3 scripts/validate-metadata.py --name "[name]" --description "[description]"
ArgumentoObligatorioQué comprueba
--nameSíLongitud de 1 a 64 y el patrón ^[a-z0-9]+(-[a-z0-9]+)*$.
--descriptionNoLongitud máxima de 1.024 caracteres y ausencia de palabras en primera o segunda persona.

Las tres salidas, tal como se producen

$ python scripts/validate-metadata.py --name "skill-creator" \
    --description "Authors and structures professional-grade agent skills following the agentskills.io spec."
SUCCESS: Metadata is valid and optimized for discovery.
# código de salida: 0
$ python scripts/validate-metadata.py --name "Skill_Creator" --description "Authors skills."
NAME ERROR: 'Skill_Creator' contains invalid characters. Use only lowercase letters, numbers, and single hyphens. No consecutive hyphens, and cannot start/end with a hyphen.
# código de salida: 1
$ python scripts/validate-metadata.py --name "skill-creator" \
    --description "I help you create skills for your agent."
STYLE WARNING: Description contains first/second person terms: {'i', 'you', 'your'}. Use third-person imperative (e.g., 'Creates...', 'Updates...').
# código de salida: 1
SalidaQué significaQué se hace
0Los metadatos son válidos y están optimizados para el descubrimiento.Se continúa al paso 2.
1Hay al menos un error. El prefijo del mensaje dice de qué tipo: NAME ERROR, DESCRIPTION ERROR o STYLE WARNING.Se identifica el error concreto, se reescribe el campo y se vuelve a ejecutar hasta obtener 0.

Dos detalles que conviene conocer antes de usarlo. STYLE WARNING se comporta como un error: sale con código 1 y bloquea el paso. Y la comprobación de estilo es una heurística por palabras completas —i, me, my, we, our, you, your—, así que describe lo que detecta, no todo lo que un revisor humano vería.

El script tampoco obliga a pasar --description: con el valor por defecto vacío devuelve éxito. La longitud se comprueba sobre el texto que recibe.

4

Estructura del directorio

Con el nombre ya validado, la estructura no se improvisa: cuatro entradas, ni una más, y el contenido de las tres carpetas siempre a un nivel de profundidad.

distintivo-visual/
├── SKILL.md              # obligatorio: metadatos + procedimiento
├── scripts/              # CLIs minúsculas y lógica determinista
├── references/           # contexto plano: esquemas, documentación de API
└── assets/               # plantillas de salida, esquemas JSON, ficheros estáticos
CarpetaPara quéCondición
scripts/Herramientas CLI minúsculas y lógica determinista.Un solo propósito por script; nada de código de librería.
references/Contexto plano: esquemas, documentación de API, conjuntos de reglas.Un nivel de profundidad y enlazado desde SKILL.md.
assets/Plantillas de salida, esquemas JSON y ficheros estáticos.Se copian o se leen, no se interpretan.

Las cuatro condiciones que se comprueban

  • Un solo nivel: references/schema.md sí; references/db/v1/schema.md no.
  • Solo tres carpetas estándar: scripts/, references/ y assets/.
  • Ningún fichero para personas: README.md, CHANGELOG.md o INSTALLATION_GUIDE.md no tienen sitio dentro de la skill.
  • Barras inclinadas: todas las rutas que aparecen en SKILL.md son relativas y usan /, sea cual sea el sistema operativo.

Por qué se prohíbe la documentación dentro. Una skill se carga en la ventana de contexto del agente; un README.md dentro del paquete es contexto que se paga y no se usa. La documentación del proyecto va fuera del paquete, en docs/, donde no consume nada. Esta misma página vive ahí.

5

Redactar SKILL.md

Se copia la estructura de la plantilla, no se describe. El texto se escribe para un agente: secuencia cronológica, decisiones explícitas y términos idénticos de principio a fin.

La plantilla, tal como está en assets/SKILL.template.md

---
name: [skill-name]
description: [Action-oriented capability description in the third person. Max 1,024 characters. Include positive triggers. Do not use for [explicit negative triggers].]
---

# [Skill Title]

## Procedures

**Step 1: [Action Phase]**
1. [Third-person imperative instruction, e.g., "Extract the query parameters..."]
2. [Instruction referencing an asset, e.g., "Read `assets/template.json` to structure the final output."]

**Step 2: [Action Phase]**
1. [Decision tree/conditional logic, e.g., "If source maps are required, run `scripts/build.sh`. Otherwise, skip to Step 3."]
2. [Instruction requiring JiT loading, e.g., "Read `references/auth-flow.md` to map the specific error codes."]
3. Execute `python scripts/[script-name].py` to [perform deterministic action].

## Error Handling
* If `scripts/[script-name].py` fails due to [specific edge case], execute [recovery step].
* If [condition B occurs], read `references/[troubleshooting-file].md`.

Las cinco reglas de redacción

voz

Imperativo, tercera persona

Órdenes directas: «Extract the text», «Run the build». Ni «Voy a extraer» ni «Deberías extraer».

orden

Secuencia numerada

El flujo es cronológico y estricto. Cada árbol de decisión se escribe completo, con la condición y el salto.

forma

Plantillas, no descripciones

Si la salida tiene estructura, la plantilla va en assets/ y se ordena copiarla en lugar de describirla con párrafos.

lenguaje

Terminología idéntica

Un término por concepto, y el más propio del dominio: en Angular, «template» y no «html», «markup» o «view».

Divulgación progresiva

  • El SKILL.md principal se queda por debajo de 500 líneas.
  • Un esquema grande, un conjunto de reglas complejo o contexto voluminoso se mueve a un fichero plano de references/.
  • El agente recibe la orden de leerlo solo cuando hace falta, no antes: eso es la carga justo a tiempo.
Read references/api-spec.md to identify the correct endpoint.

La instrucción de carga es parte del contrato: sin ella, el fichero existe y nadie lo abre.

6

Scripts deterministas

Lo que no debe variar no se le pide al modelo: se empaqueta como un CLI minúsculo que devuelve éxito o fallo con un mensaje que el agente puede usar para corregirse.

Qué se delegaCómo se diseña
Tareas frágiles: expresiones regulares, análisis complejo, código repetitivo.Un script de un solo propósito en scripts/, con argumentos explícitos.
Comunicación del resultado.stdout para el éxito, stderr para el fallo, con mensajes descriptivos y legibles.
Errores que el agente debe poder corregir solo.Mensajes que digan qué campo falla y qué forma se esperaba, sin intervención de la persona.
Lógica de librería de larga vida.Fuera: pertenece a las CLI estándar del repositorio, no al paquete de la skill.

El validador de metadatos de esta propia skill es el modelo: declara sus argumentos, imprime el éxito por stdout, imprime cada error con un prefijo estable por stderr y devuelve código 1 cuando hay algo que corregir.

La prueba de que un script está bien escrito es que el agente pueda autocorregirse con su salida. Si un mensaje de error obliga a abrir el código fuente para entenderlo, el script no está terminado: está escrito para una persona que lo depura.

7

Composición de skills

El paso 5 es opcional y solo aplica a skills complejas. En lugar de un cuerpo que lo hace todo, una skill de alto nivel que deriva a otras según la condición.

  • Se crea una skill enrutadora de alto nivel.
  • Sus disparadores condicionales apuntan a otras carpetas de skill concretas.
  • La derivación se escribe como una orden, no como una sugerencia: «To build the client, see [path to client-build skill]».

Si la skill no es compleja, este paso se salta. Añadir una capa de enrutado a un procedimiento de tres pasos solo añade una lectura más.

8

Validación final y checklist

El paso 6 es una auditoría, no una relectura: se buscan los puntos donde el agente se vería obligado a adivinar y se contrasta el resultado con la checklist completa.

Las tres comprobaciones del paso 6

  • Huecos de alucinación: cualquier punto donde el agente tenga que suponer un paso, una ruta o un formato.
  • Rutas: todas relativas y con barras inclinadas.
  • Contraste final: el resultado se compara con references/checklist.md.

9

Errores y autocorrección

La skill nombra dos fallos y su salida. No hay un tercero documentado: si aparece algo distinto, no está cubierto por el procedimiento.

Falla el validador de metadatos

Primero se identifica el error concreto por su prefijo —por ejemplo STYLE ERROR— y después se reescribe el campo eliminando los pronombres de primera y segunda persona. No se cambia el nombre del campo ni se desactiva la comprobación: se corrige el texto y se vuelve a ejecutar.

El borrador se hincha de contexto

Si el SKILL.md supera las 500 líneas, se extrae el bloque procedimental más grande y se mueve a un fichero de references/. Lo que se queda en el cuerpo principal es la orden de leerlo cuando toque.

Por qué solo dos. Un procedimiento que enumera todos los errores posibles promete una cobertura que no tiene. Estos dos son los que el propio ciclo detecta —el validador y el contador de líneas—, y son los únicos sobre los que la skill afirma una conducta.

13

Preguntas cortas

Las dudas que aparecen al crear la primera skill, con la respuesta que da el procedimiento.

¿Por qué el name tiene que ser igual que la carpeta?

Porque el nombre es el identificador con el que se enruta la skill y la carpeta es el sitio donde vive. Si no coinciden, la ruta del fichero y los metadatos dicen cosas distintas.

¿Puedo saltarme el validador?

No dentro del procedimiento: el paso 1 exige ejecutarlo y corregir hasta que devuelva 0. Es la única puerta automática que separa los metadatos válidos de los que solo parecen razonables.

El validador dice STYLE WARNING y sale con 1. ¿Es un aviso?

No. Aunque el mensaje diga «warning», devuelve código 1 y bloquea el paso: hay que reescribir la descripción sin pronombres de primera o segunda persona.

¿De verdad hay un límite de 500 líneas?

Sí, y es una condición de la checklist. Al superarlo, el bloque procedimental más grande se mueve a references/ y el cuerpo principal conserva la orden de leerlo.

¿Puedo crear una cuarta carpeta si mi skill lo necesita?

La estructura estándar son tres: scripts/, references/ y assets/. Añadir otra es una decisión de diseño que la skill no contempla; si el contenido no encaja en ninguna, el problema está en la forma de la skill, no en la lista de carpetas.

¿Un README.md dentro de la skill, aunque sea corto?

No. La lista de ficheros para personas que no deben existir incluye README.md, CHANGELOG.md e INSTALLATION_GUIDE.md. La documentación va fuera del paquete.

¿Puedo poner un esquema grande dentro de SKILL.md?

Puedes, pero es exactamente lo que la divulgación progresiva evita: el esquema pertenece a references/ o assets/, y en el cuerpo queda solo la instrucción de leerlo cuando haga falta.

¿Los scripts pueden ser código de librería reutilizable?

No. Son CLIs de un solo propósito. La lógica de librería de larga vida pertenece a las CLI estándar del repositorio.

¿Cómo sabe el agente cuándo abrir una referencia?

Porque el SKILL.md se lo ordena explícitamente, nombrando el fichero y la situación. Los recursos no se cargan solos: la carga justo a tiempo es una instrucción, no una expectativa.

¿Cuándo uso la composición?

Solo si la skill es compleja y necesita derivar a otras. Es un paso opcional; para un procedimiento corto, añadir una skill enrutadora es una lectura de más.

¿Qué hago si mi skill no es para un agente?

No uses esta skill. Sus disparadores negativos excluyen la documentación general y el código de librería que no es para un agente.

¿La checklist se puede pasar a medias?

No: todas las casillas deben estar en «Pass» antes de considerar la skill desplegable. Una casilla sin marcar es un defecto, no una deuda pendiente.

Cómo se usa en este repositorio

El paquete no es de autoría propia: está fijado en .skills/ y se usa tal cual, sin editarlo, cuando hace falta crear una skill nueva en src/.

RutaQué esQué implica
.skills/skill-creator/La skill de terceros, fijada a una versión concreta.No se edita aquí: se actualiza sustituyéndola.
src/<skill>/Las skills propias del repositorio.Contienen solo lo que el agente necesita para ejecutarlas.
docs/<skill>/La documentación de cada skill.Vive fuera del paquete, así que no consume contexto.

La regla de empaquetado del repositorio coincide con la del paso 2: dentro de src/<skill>/ no se crean README.md, CHANGELOG.md ni guías de instalación. La documentación del proyecto vive en docs/ y en la raíz.

Contrato completo y política. La estructura del repositorio está descrita en el README, y la política de ramas, commits e integración en CONTRIBUTING.md. Esta página documenta la skill, no el flujo del repositorio.

Los dos son navegables: se puede cambiar el tema, alternar el estilo visual, trazar una ruta entre dos nodos, buscar por etiqueta y exportar a SVG, PNG, WebM o tarjeta para compartir.

# requiere archify 3.2.0 (github.com/tt-a1i/archify, tag v3.2.0)
node <ruta-a-archify>/archify/bin/archify.mjs deliver workflow \
  docs/skill-creator/flujo-de-trabajo.json \
  docs/skill-creator/flujo-de-trabajo.html --quality showcase

node <ruta-a-archify>/archify/bin/archify.mjs deliver architecture \
  docs/skill-creator/arquitectura.json \
  docs/skill-creator/arquitectura.html --quality showcase

Cómo se generan. Los dos son artefactos de archify 3.2.0: un candidato JSON describe el diagrama y el renderizador produce un HTML autónomo con temas, movimiento y exportación. Los candidatos —flujo-de-trabajo.json y arquitectura.json— están al lado de cada página, así que se corrigen y se vuelven a entregar con la CLI de archify 3.2.0, que escribe su recibo .delivery.json junto al HTML con los sha256 del spec y del artefacto. La entrega es reproducible: el mismo spec devuelve el mismo HTML.
