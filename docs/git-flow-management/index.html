Git con ceremonia proporcional

La skill git-flow-management conduce las operaciones de Git como un procedimiento verificable: clasifica la tarea por tamaño y riesgo, inspecciona en solo lectura antes de tocar nada, deja los cambios preparados en el stage con su mensaje y espera confirmación explícita antes de ejecutar. Una tarea pequeña puede ir directa a main; una normal o compleja pide rama corta. Lo que no se puede probar con comandos de solo lectura no se declara terminado.

1

Qué hace

Trata Git como un procedimiento con evidencia en los dos extremos: mira el estado antes de decidir y prueba el resultado antes de llamarlo terminado. La ceremonia crece con el riesgo; la costumbre no la justifica.

SituaciónQué hace la skill
Hay que tocar Git: una rama, un commit, una integración, una release, un hotfix, un conflicto, una publicación o una recuperación.Clasifica la tarea por tamaño y riesgo, y aplica la ceremonia mínima que mantiene el resultado fiable.
La tarea es pequeña y el riesgo está contenido.Permite el trabajo directo en main, con rutas enumeradas, diff revisado, mensaje en inglés y confirmación antes de crear el commit.
La tarea es normal o compleja, o el árbol ya tiene cambios ajenos.Propone una rama corta antes de modificar archivos y presenta un plan con las etapas, el mensaje exacto y el resultado esperado.
El resultado no coincide con el plan, o no hay forma de demostrarlo.Se detiene, inspecciona y prepara un plan nuevo. El cierre queda como INCOMPLETO o NO VERIFICADO, no como terminado.

Lo que no hace. No impone Git Flow a un repositorio que no lo declara, no inventa develop, pull requests, SemVer ni etiquetas, no ejecuta nada persistente sin confirmación y no da por bueno un cambio porque los comandos no hayan fallado.

3

Cómo se usa

Cinco momentos, siempre en el mismo orden. El tamaño de la tarea cambia la profundidad de cada uno, no cuáles se hacen.

clasificarMide

Tamaño y riesgo antes de cualquier comando que persista. De aquí sale si hay rama, cuántos commits y cuánta verificación.

inspeccionarObserva

Solo lectura y sin confirmación: rama actual, árbol de trabajo y, si la tarea es normal o compleja, ramas, remoto e historial.

proponerPresenta

Las etapas que se van a ejecutar, las rutas, el mensaje exacto en inglés y el comando que probará el resultado.

confirmarEspera

La respuesta autoriza solo lo enumerado. Otra rama, otro conjunto de archivos, un conflicto o un remoto nuevo invalidan el permiso.

verificarPrueba

Estado, ascendencia e integración con comandos de solo lectura. Sin esa evidencia el cierre es INCOMPLETO o NO VERIFICADO.

git status --short --branch

scripts/verify-branch.sh <ancestro> <descendiente> [remoto]

El script sale con 0

La contención se verifica: el ancestro está contenido en el descendiente. Es la evidencia que se muestra al cerrar una integración y la que confirma que el commit de base es el que se creía.

El script sale con 1

La contención no se cumple. No se trata como un detalle: se informa de lo que falta y se revisa si el origen y el destino del plan están invertidos antes de proponer nada.

El script sale con 2

Uso inválido: faltan argumentos, el directorio no está dentro de un repositorio, una referencia no resuelve o el remoto no está configurado. Se corrige el argumento; no se sustituye la comprobación por una lectura a ojo.

Ningún commit se ejecuta sin confirmación explícita

Los cambios quedan preparados en el stage, con el mensaje ya redactado y el diff mostrado, y se espera la respuesta. Si al revisar el diff preparado el alcance debe cambiar, se vuelve atrás y se pide una confirmación nueva. Antes de ejecutar, se revalidan rama, HEAD y árbol de índice; si algo cambió, la confirmación no vale. Si el índice ya tenía cambios ajenos al plan, el flujo se detiene antes de preparar.

Una confirmación, varias etapas —y un límite. Se pueden presentar juntas la rama, la preparación, el commit, la integración y el borrado, y recibir un solo «sí». Ese «sí» no cubre un push, no se hereda a trabajo posterior y se cae si una etapa falla o el estado cambia. Cualquier operación remota se confirma aparte, aunque el commit ya esté hecho.

6

Preguntas cortas

Lo que casi todo el mundo pregunta en la primera conversación.

¿En qué idioma va el mensaje de commit?

En inglés: tipo, ámbito opcional y descripción en imperativo, con el formato Conventional Commits; por ejemplo fix(cli): reject empty paths. El resto del proyecto sigue el idioma que le corresponda.

¿Por qué no git add .?

Porque prepara todo lo que haya, incluido lo que no forma parte del encargo. Se preparan rutas enumeradas, y si de verdad todo pertenece junto, el plan explica por qué.

¿Puedo hacer rebase de mi rama?

Solo si es privada y no está publicada. Una rama compartida o ya publicada no se rebasa ni se aplasta sin una regla documentada y una aprobación explícita.

Me equivoqué con un commit. ¿reset --hard?

Primero se inspecciona el estado, el historial y el reflog, y se prefiere revertir o un commit correctivo. Un reset destructivo exige autorización para ese comando concreto, con las consecuencias expuestas, y se verifica antes de dar el paso siguiente.

¿Por qué el cierre dice NO VERIFICADO y no INCOMPLETO?

Porque son cosas distintas. INCOMPLETO significa que una condición obligatoria falló o no se ejecutó; NO VERIFICADO, que no hay evidencia suficiente para afirmar nada. La skill prefiere el segundo antes que una conclusión sin pruebas.

¿Sirve para un repositorio sin remoto?

Sí. Un flujo local no incumple nada por no tener remoto: las comprobaciones contra el remoto simplemente no aplican. Esa ausencia no se convierte en un incumplimiento inventado.

Verificación

La contención de ramas y la puerta del repositorio se ejecutan antes de cerrar; sin esa evidencia el cierre es INCOMPLETO o NO VERIFICADO.

src/git-flow-management/scripts/verify-branch.sh   [remoto]
python3 scripts/check-repo.py
CódigoSignificado
0La rama descendiente contiene al ancestro; el cierre puede declararse.
1La contención no se cumple.
2Uso inválido o un comando Git no disponible.

La contención demuestra que el commit está dentro de la rama; no sustituye la revisión del plan de integración ni autoriza el push.
