Git con ceremonia proporcional

Esta skill no impone Git Flow a todo: clasifica la tarea, aplica la ceremonia mínima que mantiene el resultado fiable y deja siempre el commit a la espera de una confirmación explícita. En una tarea pequeña se permite el commit directo en main; en una normal o compleja se propone rama corta. Si no se puede probar el resultado, no está terminado.

Qué es esta skill

Un procedimiento, no una intención. La diferencia se nota cuando algo sale mal: aquí siempre hay una inspección previa y una prueba posterior.

La skill se llama git-flow-management en su frontmatter y vive en la carpeta git-flow-management/. Es obligatoria para cualquier operación Git: no se puede continuar un flujo ignorando sus comprobaciones porque alguien haya dicho «haz Git Flow», «haz un commit» o «sube los cambios».

Su ciclo tiene cuatro partes y ninguna es opcional: clasificar la tarea por tamaño y riesgo, inspeccionar en solo lectura, preparar y presentar el commit o el plan completo, ejecutar solo lo confirmado y probar el resultado. La skill nunca promete lo que no ha comprobado.

El bucle completo, en cuatro pasos

clasificaciónMide

Pequeña, normal o compleja. De aquí sale cuánta ceremonia hace falta: rama o no, cuántos commits y cuánta verificación.

inspecciónObserva

Un git status basta en una tarea pequeña; en normales y complejas se añaden ramas, remoto e historial. No requiere confirmación.

commitConfirma

Los cambios quedan preparados en el stage con su mensaje Conventional Commits en inglés. Se ejecuta solo lo que la confirmación enumera.

verificaciónPrueba

Estado, commit, ascendencia, referencias remotas y validación acordada, en la proporción que la tarea exige. Sin evidencia, el resultado es INCOMPLETO o NO VERIFICADO.

La regla mental. La unidad de trabajo de esta skill no es el comando: es el commit confirmado. Un cambio fuera del stage no está listo, y un commit sin confirmación es una decisión que el usuario no tomó.

Las once invariantes

Son obligatorias y no admiten interpretación. Cada una existe porque su ausencia produce un daño concreto y difícil de deshacer.

#InvarianteQué impide
1La skill es obligatoria para cualquier operación Git.Que una frase como «haz un commit» desactive las comprobaciones.
2No se declara aplicado, integrado, publicado ni terminado nada sin verificarlo con comandos de solo lectura y mostrar el resultado.Los «hecho» sin evidencia.
3La política documentada del repositorio prevalece sobre cualquier modelo genérico. Si no declara política, se aplica el modelo por defecto: main como línea estable y ramas cortas cuando la tarea lo justifica.Imponer un modelo a un repositorio que ya tiene el suyo.
4Ningún commit se ejecuta sin confirmación explícita: los cambios se dejan preparados en el stage, se propone el mensaje exacto y se espera la respuesta.Que el commit se adelante a la aprobación.
5La confirmación no es global ni reutilizable: cubre solo las etapas que enumera y el estado mostrado. Otra rama, otro conjunto de archivos, un conflicto, un push nuevo o una discrepancia la invalidan.Reutilizar un «sí» para algo que el usuario no aprobó.
6Varias etapas pueden presentarse juntas y confirmarse de una vez, pero nunca se aprovecha una confirmación previa para una etapa que no estaba en ella.Encadenar trabajo nuevo bajo un permiso viejo.
7No se amplía el alcance: nada de add global, cambios ajenos, no rastreados ni amend, salvo que el plan aprobado lo nombre expresamente.Commits que arrastran trabajo de otro.
8Nada de reset destructivo, clean, restauración desde otra revisión, borrado forzado de ramas, push forzado, borrado de etiquetas o ramas remotas, ni reescritura de historia, salvo autorización específica para ese comando.Pérdida irreversible de trabajo.
9develop, cuando existe, es rama protegida: nunca se prepara trabajo normal sobre ella. main admite trabajo directo solo en tareas pequeñas y de riesgo contenido, siempre con stage revisado y confirmación posterior.Ceremonia inútil en un lado y trabajo normal colado en producción en el otro.
10Cualquier operación remota —push, fetch para integrar, pull o creación de referencias remotas— requiere confirmación propia, aunque el commit ya esté hecho y confirmado.Publicar sin que nadie lo haya pedido.
11Ante conflicto, estado inesperado, error o resultado distinto al plan: detente, no improvises una resolución, inspecciona y prepara un plan nuevo.Resoluciones inventadas bajo presión.

El error que estas reglas evitan. Casi todos los desastres de Git no vienen de un comando difícil, sino de una cadena de decisiones razonables tomadas sin mirar el estado. La invariante 11 existe porque el momento de parar es justo cuando el resultado no coincide con el plan.

Inspección proporcional

Es de solo lectura y no pide permiso. Se ejecuta antes de proponer cualquier operación persistente, y su extensión depende del tamaño de la tarea.

Comprobación de entrada, siempre

git status --short --branch

Basta para una tarea pequeña y no se repite tras cada paso: sirve para conocer la rama y detectar cambios previos. Esos cambios del usuario se conservan; si afectan a los archivos que vas a tocar, se dicen antes de continuar.

Antes de una operación persistente normal o compleja

Amplía la mirada al historial, las ramas y el remoto:

git branch --show-current
git branch -a -vv
git remote -v
git log --graph --oneline --decorate --all -n 30

Y lee la documentación de contribución y de flujo si existe: es la evidencia más fuerte para clasificar el repositorio y la que decide si el modelo por defecto se aplica o no.

Para operaciones acotadas: inspección ampliada

La referencia de operaciones normales añade el detalle que hace falta antes de preparar archivos y commits. Separa explícitamente lo modificado, lo no rastreado, lo ya preparado, los archivos generados y los cambios ajenos al encargo.

git status --short --branch
git diff --stat
git diff -- <paths>
git diff --cached --stat
git diff --cached -- <paths>
git log --oneline --decorate -n 12
PREV
Lo que hay que saber antes de empezarLa rama actual, el tamaño de la tarea y si hay cambios previos que se puedan mezclar con el trabajo nuevo. Con eso se decide si hace falta rama o si basta el commit directo en main.
4

Clasificar el repositorio

Antes de aplicar reglas hay que saber qué repositorio se tiene delante. La clasificación decide si se aplica el modelo por defecto, se respeta uno declarado o se pide una decisión. La proporcionalidad decide la ceremonia, no el modelo de ramas.

Las cinco categorías

ClasificaciónQué significaQué se hace
Modelo por defectoNo hay política declarada y main es la única rama de larga vida, o ya se usan ramas cortas desde ella.Aplicar proporcionalidad: rama solo cuando la tarea no es pequeña. No inventar develop.
Git Flow declaradoDocumento o práctica verificable con main, develop y ramas de trabajo asociadas.Respetar su tabla de bases y destinos desde el siguiente trabajo.
Git Flow documentado, pendiente de evidencia operativaExiste una guía aplicable, pero el historial aún no demuestra una feature, release o hotfix completados.Tratar la guía como política obligatoria; no declarar práctica demostrada.
Política existente distintaOtro modelo de ramas, ya en uso.Conservarlo; no añadir Issues, PR, SemVer, etiquetas ni reglas de merge que no declare.
DesconocidaEvidencia contradictoria o inexistente.Exponer la evidencia y pedir decisión antes de cualquier operación persistente.

Jerarquía de evidencia

Cuando las señales no coinciden, manda la más fuerte. El orden es este y no se invierte:

  • 1. Documentación que declara una política operativa o su precedencia.
  • 2. Ramas remotas activas, protecciones conocidas y mecanismos de revisión.
  • 3. Historial de integración y relaciones entre ramas.
  • 4. Ramas locales y convenciones de nombre.

Dos trampas clásicas. Que exista un documento no prueba que el flujo se haya ejecutado correctamente. Y que exista una rama llamada develop tampoco prueba Git Flow. La skill distingue siempre tres cosas: política declarada, estructura presente y uso demostrado.

La regla de adaptación

En un repositorio existente, una guía explícita puede obligar el siguiente trabajo aunque la historia no haya dado todavía una prueba operativa. Eso no autoriza a migrar ni a inventar infraestructura. Para una política documental sobria:

  • No añadir Issues, PR obligatorias, SemVer, remoto ni reglas de merge si el documento no los exige.
  • Usar el patrón de nombre que especifique el documento.
  • No convertir la ausencia de remoto en un incumplimiento del flujo local.

Proporcionalidad no es laxitud. Si el repositorio declara ramas de trabajo obligatorias, una tarea pequeña no autoriza a saltárselas. Si no declara nada, una tarea pequeña no obliga a abrir rama.

Modelo de ramas

Dos modelos posibles y uno por defecto. Lo que cambia con el tamaño de la tarea es cuánta ceremonia se aplica, no qué modelo se inventa.

Clasificación proporcional

TamañoRamaCommitVerificación
Pequeña
texto, documentación, configuración, corrección localizada		No obligatoria. Trabajo directo en main permitido.Un commit coherente, siempre confirmado.Revisar el diff y una comprobación localizada si existe.
Normal
funcionalidad completa, corrección de varios archivos		Rama corta recomendada si estás en main.Un commit coherente; varios solo con una razón.Validación principal del proyecto.
Compleja
cambio incompatible, migración, reestructuración amplia		Rama específica obligatoria.Varios commits por unidad funcional cuando aporten recuperación.Validación principal más comprobaciones de los puntos críticos.

Señales de que la tarea no es pequeña: toca código ejecutable en varios módulos, cambia datos, contratos públicos, seguridad o concurrencia, o no sabrías deshacerla con una lectura del diff. Ante la duda razonable, se trata como la categoría superior.

El modelo por defecto: main y ramas cortas

  • main contiene lo que está listo para usarse y no se abandona por reflejo.
  • Las ramas de trabajo se crean desde main y viven lo mínimo: feature/<slug>, fix/<slug>, docs/<slug>, refactor/<slug> o chore/<slug>.
  • Sin develop, release/* ni hotfix/* por defecto.
  • La integración en main se decide aparte del trabajo: nunca se fusiona por iniciativa propia.
  • La estrategia de integración es la que mantenga el historial claro para ese repositorio; si la política documentada fija --no-ff, se respeta.

Política Git Flow, solo si el repositorio la declara

TipoBase obligatoriaDestino obligatorioPropósito
main——Código listo para producción; releases etiquetadas.
developmain—Integración de la siguiente versión.
feature/<id>-<slug>developdevelopNueva funcionalidad.
fix/<id>-<slug>developdevelopCorrección no productiva.
release/<version>developmain y después developPreparación de release.
hotfix/<id>-<slug>mainmain y después developCorrección urgente de producción.

Reglas que acompañan a la tabla

  • develop se crea desde el commit inicial de main.
  • Cada rama de trabajo se crea desde su base obligatoria y se verifica la relación antes de trabajar en ella.
  • Se integra en ramas protegidas mediante PR cuando exista un mecanismo de revisión configurado; un merge local directo no es sustituto sin explicarlo.
  • Nada de squash ni rebase de una rama compartida o publicada sin regla documentada y aprobación explícita.
  • Se conserva el back-merge de toda release y hotfix hacia develop.
  • Si no existe sistema de incidencias, se usa feature/<slug> o fix/<slug>: no se inventa un identificador.
  • No se presupone que la extensión git-flow está instalada: se usa Git normal.

El back-merge no es un detalle. Es lo que evita que la siguiente release reabra un fallo ya corregido en producción. Por eso toda release y todo hotfix se integran en los dos destinos, y se verifica que ambos contienen el resultado.

Commit, plan y confirmación

Ningún commit se ejecuta sin confirmación previa. Los cambios se dejan preparados en el stage, con su mensaje ya redactado, y la respuesta del usuario decide si se ejecuta.

Protocolo de commit, en seis pasos

  1. Preparar únicamente las rutas que el plan enumera.
  2. Revisar y mostrar el diff preparado.
  3. Redactar el mensaje con Conventional Commits, nombre y descripción en inglés.
  4. Presentar archivos, mensaje exacto, validación realizada, cuántos commits se proponen y cualquier hallazgo que requiera decidir algo. Los hallazgos se dicen antes del commit, no después.
  5. Pedir confirmación explícita para ese commit o para los commits coherentes de la tarea.
  6. Ejecutar exactamente el mensaje confirmado y verificar SHA, mensaje y archivos.
git add -- src/module.ts tests/module.test.ts
git diff --cached

git commit -m "feat(cli): add staged commit confirmation"
git show --stat --oneline HEAD

Si tras revisar el diff preparado el alcance debe cambiar, se vuelve al primer paso y se pide una confirmación nueva. Un mensaje confirmado no se reescribe por conveniencia.

Qué hace útil a cada bloque

Estado detectado

Fija el punto de partida y el tamaño de la tarea. Si mañana algo no cuadra, este bloque es la referencia de qué se creía cierto al aprobar.

Plan propuesto

Enumera etapas, archivos, ramas y el mensaje exacto de commit. «Resultado verificable esperado» obliga a escribir qué comando probará que se cumplió.

Confirmación

Una pregunta cerrada: se aprueban esas etapas y ese mensaje, o no se ejecuta nada. No hay confirmaciones parciales ni «adelanta lo que puedas».

Etapas agrupadas

  • Se pueden proponer varias etapas juntas —crear la rama, preparar, commitear, integrar, borrar la rama, publicar— y recibir una sola confirmación que las cubra todas.
  • La confirmación enumera las etapas que autoriza: lo que no enumere sigue sin autorizar.
  • No se hereda a trabajo posterior, a otro conjunto de archivos ni a otro push.
  • Si una etapa falla o el estado cambia, las restantes quedan sin autorizar y requieren un plan nuevo.

Después de la confirmación

  • Se ejecuta solo lo confirmado, comando por comando.
  • Antes de cada comando remoto incluido, se revalida que el estado no ha cambiado.
  • Si el estado cambió, se detiene la ejecución y se solicita un plan nuevo.
  • Un conflicto, un error o un resultado distinto al previsto es una parada, no una adaptación.

Por qué se confirma una vez y no se reaprovecha. Pedir permiso a cada paso invita a aprobar sin leer; reutilizar un «sí» viejo invita a ejecutar algo que nadie aprobó. La skill resuelve la tensión con dos límites: la confirmación enumera exactamente qué se toca, y cualquier desviación la invalida por completo.

Guardia de ramas

La comprobación que más trabajo ahorra. Antes de preparar archivos o proponer un commit se mira la rama actual y el tamaño de la tarea: juntos deciden si hay rama o no.

Rama actualTamaño de la tareaResultado obligatorio
mainPequeñaPermitir trabajo directo: preparar rutas, revisar el diff, proponer mensaje y pedir confirmación.
mainNormal o complejaProponer una rama corta desde main y confirmarla antes de modificar archivos.
developCualquier trabajoBloquear y proponer feature o fix desde develop.
mainIntegrar una rama de trabajoPermitir solo tras verificar origen, destino y plan aprobado.
developIntegrar feature, fix, release o hotfixPermitir solo tras verificar origen, destino y plan aprobado.

Qué hace pequeña a una tarea

  • El diff es pequeño y su efecto se entiende leyéndolo.
  • No toca datos almacenados, contratos públicos, seguridad, concurrencia ni código ejecutable en varios módulos.
  • No hay cambios del usuario mezclados en los archivos afectados.
  • Se deshace revirtiendo el commit, sin reescribir historia.

Si alguna condición no se cumple, no es pequeña. Ante la duda, se propone una rama: cuesta un comando.

Trabajo directo en main

Permitido en tareas pequeñas, con estas condiciones:

  • Se preparan rutas enumeradas, nunca un add global.
  • Se revisa git diff --cached y se muestra.
  • Se propone el mensaje Conventional Commits en inglés.
  • Se pide confirmación explícita antes de ejecutar el commit.
  • Se verifica el commit y el estado del árbol después.

No hay una excepción documentada que haya que demostrar: la proporcionalidad es la regla.

Evidencia de una integración

Toda integración hacia una rama protegida debe identificar origen y destino permitidos, commits incluidos, mecanismo de revisión si existe, estrategia de merge, la comprobación posterior de que el resultado está contenido en el destino, y si la rama se borra después.

Si la rama actual no es la permitida, no se arregla con checkout, rebase o merge por iniciativa propia. Se explica la discrepancia y se prepara un plan separado: mover trabajo de rama también es una operación que se aprueba.

8

Ramas, commits y push

Nombres predecibles, mensajes en inglés y un commit que un revisor puede leer de uno en uno. La convención no es estética: es lo que permite saber qué contiene cada integración.

Nombres de rama

  • Minúsculas y palabras separadas por guiones.
  • En el modelo por defecto la base es main: feature/<slug>, fix/<slug>, docs/<slug>, refactor/<slug> o chore/<slug>.
  • Con Git Flow declarado se respeta su base obligatoria: feature/<id>-<slug>, fix/<id>-<slug>, hotfix/<id>-<slug> y release/<version>.

Antes de crear la rama, se verifica la base:

git merge-base --is-ancestor <base> HEAD
git log -1 --oneline <base>

Si la base está desactualizada frente a su upstream, se informa del estado y se propone actualizarla como operación separada y confirmada.

Mensaje de commit

Formato de Conventional Commits, con nombre y descripción en inglés:

<type>(<scope opcional>): <descripción en imperativo, en inglés>
  • Tipos habituales: feat, fix, docs, chore, refactor, test, style, perf, ci, build y revert.
  • Un commit representa un cambio lógico coherente, no un archivo ni un paso intermedio.
  • Por defecto, una tarea completa cabe en un commit aunque afecte a varios archivos.
  • Varios commits solo con una razón clara: separar cambios independientes, facilitar una revisión concreta o conservar una recuperación útil.
  • Descripción breve, en imperativo, en inglés y sin punto final.
  • Sin firmas de IA ni líneas Co-Authored-By salvo solicitud expresa.
  • Una ruptura se marca con ! o con un pie BREAKING CHANGE.
  • El cuerpo puede nombrar la tarea que lo sostiene, por ejemplo Refs: tk-141, cuando el proyecto usa un tablero.

Preparación segura

  1. Inspeccionar cambios rastreados, no rastreados y ya preparados.
  2. Separar explícitamente lo que queda fuera del commit.
  3. Preparar únicamente rutas enumeradas: git add -- <rutas>.
  4. Revisar el diff preparado con git diff --cached y mostrarlo.
  5. Presentar el mensaje exacto y pedir confirmación antes de commitear.
  6. Ejecutar el commit confirmado y verificar SHA, mensaje y archivos.

git add . y git add -A requieren un plan que explique por qué todos los cambios pertenecen juntos. En la práctica, casi nunca es cierto: siempre hay un archivo temporal, un log o una prueba que no debía entrar.

Push

Cualquier push, incluido el de una rama nueva, requiere confirmación previa específica y revalidación del estado justo antes de ejecutarlo. Un commit confirmado no autoriza a publicarlo.

git push -u origin <rama>
git ls-remote --heads origin

La verificación posterior al commit es corta y suficiente: git show --stat --oneline HEAD y git status --short --branch. Si el SHA no existe o el diff no coincide con los archivos aprobados, el paso no está terminado.

9

Integración, conflicto y borrado

Integrar una rama es una decisión distinta de trabajar en ella, y borrarla es una tercera decisión. Ninguna ocurre por inercia.

La integración se decide aparte

Se puede incluir en el plan junto con el commit y el borrado de la rama, y recibir una sola confirmación que enumere las tres etapas. Lo que no se hace es fusionar por iniciativa propia. Antes de integrar se comprueba brevemente:

  • Que la tarea está terminada y la validación acordada se ha ejecutado.
  • Que no hay cambios del usuario que vayan a perderse.
  • Que la rama que se integra es la correcta y deriva de la base esperada.

La estrategia la fija la política del repositorio; si no fija ninguna, se elige la que mantenga el historial claro y sencillo para ese repositorio. --no-ff no es obligatorio por sí mismo.

MétodoCuándo usarloCuándo no
mergeLa rama es compartida o la política conserva topología.La política exige linealidad.
rebaseLa rama es privada y no publicada.La rama se comparte o ya está publicada.
cherry-pickDebe trasladarse un commit aislado.Debe integrarse una rama completa.

El plan previo de integración

Antes de tocar nada se muestra: origen, destino, commits incluidos, ancestro común, posibilidad de fast-forward, efecto sobre la historia, validación y riesgo de conflicto. Con eso, la decisión de integrar deja de ser una apuesta.

Después de integrar

  1. Comprobar el estado final y mostrar la contención con evidencia.
  2. Si la rama ya no se necesita, informar del nombre, del contenido integrado y del comando git branch -d <rama>, y pedir confirmación antes de borrarla.
  3. Si el usuario no confirma el borrado, dejar la rama y decirlo en el informe final.

Prefiere git branch -d, que se niega a borrar trabajo no integrado. Una rama con trabajo no integrado, o una rama remota, no se borra sin autorización específica.

Cuando aparece un conflicto

  1. Detenerse e informar de la operación y de los archivos afectados.
  2. No editar ni preparar marcadores de conflicto automáticamente.
  3. Ofrecer tres salidas: resolver archivos concretos, abortar o pausar.
  4. Para resolver, presentar una decisión semántica por archivo y pedir confirmación de un plan nuevo.
  5. Verificar que no quedan archivos sin fusionar y ejecutar la validación acordada.

Resolver un conflicto no es limpiar marcadores. Es decidir qué comportamiento sobrevive en cada archivo. Por eso la resolución es un plan nuevo con su propia confirmación: el «sí» anterior aprobaba una integración limpia, no una decisión semántica que entonces nadie había visto.

10

Release, hotfix y versionado

Dos operaciones que tocan producción y que solo existen cuando el repositorio declara Git Flow o el usuario lo encarga. Mucho en común: rama corta, cambios mínimos, dos destinos y verificación en ambos.

SemVer, solo si es aplicable

Se usa MAJOR.MINOR.PATCH únicamente si el proyecto declara Semantic Versioning o el usuario ha adoptado esa política:

ComponenteCuándo sube
MAJORCambio incompatible.
MINORFuncionalidad compatible nueva.
PATCHCorrección compatible.

Una versión no se deduce solo del tipo de commit: se comprueban los cambios públicos, el historial y la política del proyecto.

release

Siete pasos, en orden

  • Verificar que release/<version> procede de develop.
  • Limitar los cambios a estabilización, versión, notas y correcciones aprobadas.
  • Comprobar ubicaciones de versión y changelog, si existen.
  • Integrar en main mediante el mecanismo previsto, con autorización.
  • Crear etiqueta y publicación solo si están en el plan aprobado.
  • Integrar el resultado de main de vuelta a develop.
  • Verificar que ambos destinos contienen la release y proponer el borrado de la rama, con su confirmación.
hotfix

Cinco pasos, parche mínimo

  • Verificar que hotfix/<id>-<slug> procede de main.
  • Mantener el parche mínimo y validado.
  • Integrar en main y publicar etiqueta solo si procede.
  • Integrar el mismo resultado de vuelta a develop.
  • Verificar que main y develop contienen la corrección y proponer el borrado de la rama.

Una rama integrada no se borra sin decirlo. Tampoco la de release ni la de hotfix. Cuando ya no se necesita, se informa del nombre, de que su contenido está en main y del comando propuesto, y se pide confirmación. Si no la hay, la rama se queda: es justo la que querrás mirar cuando algo falle dos semanas después.

11

Verificación de cierre

Un flujo solo es COMPLETO si pasan todas las comprobaciones aplicables. Y «aplicables» depende del tamaño de la tarea: no hay «casi», pero tampoco una lista fija que se repite mecánicamente.

git status --short --branch
git log --graph --oneline --decorate --all -n 40
git merge-base --is-ancestor <ancestor> <descendant>
git branch -vv
git ls-remote --heads <remote>
git ls-remote --tags <remote>

La comprobación de ascendencia está automatizada: scripts/verify-branch.sh <ancestro> <descendiente> [remoto] informa de la contención y del estado de publicación, y su código de salida es la prueba (0 verificado, 1 no verificado, 2 uso inválido).

Comprobaciones por tamaño

TamañoObligatorio antes de cerrar
PequeñaEstado del árbol, SHA y mensaje del commit, validación localizada si existe.
NormalLo anterior más contención en main cuando hubo integración y validación principal del proyecto.
ComplejaLo anterior más comprobaciones de los puntos críticos y de cada rama implicada.

Qué se comprueba según la operación

OperaciónCondiciones que deben cumplirse
Creación de ramaLa rama existe y es la actual o está identificada; su commit de base es descendiente de la base obligatoria; no hay cambios no previstos en el árbol.
CommitEl SHA existe; el mensaje cumple el formato Conventional Commits con descripción en inglés; el diff coincide con los archivos aprobados; la validación terminó con el resultado declarado; el árbol queda en el estado anunciado.
Rama corta integrada en mainLa rama existía y derivaba de main; el resultado está contenido en main; si se borró, era la correcta, estaba integrada y su borrado se confirmó.
Feature o fix integradoLa rama fuente deriva de develop; el resultado está contenido en develop; no aparece integrado directamente en main como sustituto del paso por develop; la PR o mecanismo de revisión está identificado cuando existe.
Release integradaRelease deriva de develop; el resultado está contenido en main; el resultado de main está contenido en develop; etiqueta, versión y changelog verificados si estaban en el plan.
Hotfix integradoHotfix deriva de main; el resultado está contenido en main; el resultado de main está contenido en develop; etiqueta o publicación verificadas si estaban en el plan.
PublicaciónCada comando remoto ejecutado estaba en la confirmación que lo autorizaba; la referencia remota esperada existe y apunta al commit declarado; no hubo push forzado ni borrado remoto sin autorización específica.

Los tres estados

Completo

Todas las comprobaciones aplicables pasan.

Incompleto

Alguna condición obligatoria no se ha ejecutado o ha fallado.

No verificado

No hay evidencia suficiente para afirmar el resultado.

Antes de decir «hecho», se muestra

  1. Estado de rama y árbol de trabajo.
  2. SHA, mensaje y archivos del commit, cuando exista.
  3. Ramas, relaciones de ascendencia e integración previstas, cuando haya integración.
  4. Remoto, referencias o etiquetas publicadas, cuando aplique.
  5. La validación acordada.
  6. La lista de comprobación aplicable de la referencia de verificación.

En una tarea pequeña bastan los puntos 1, 2 y 5. Si falla una comprobación de una operación ya iniciada, el resultado es INCOMPLETO o NO VERIFICADO, no «terminado». Se explica qué condición falta y no se pasa a la siguiente fase.

12

Auditoría sin operación

Cuando el encargo solo es mirar documentación, ramas e historial, no se describe un ciclo que aún no ha empezado: se separan cuatro ejes.

EjeValores posibles
PolíticaDOCUMENTADA · NO DOCUMENTADA · CONTRADICTORIA
EstructuraPREPARADA · PARCIAL · AUSENTE
Evidencia operativaDEMOSTRADA · PENDIENTE DE PRIMER CICLO · INSUFICIENTE
Incumplimiento activoSÍ · NO · NO VERIFICABLE

Cómo se informa un repositorio recién preparado

Para un repositorio con política documental clara, main estable y sin ramas auxiliares históricas, la respuesta correcta es esta, y no un «INCOMPLETO»:

Política: DOCUMENTADA
Estructura: PREPARADA
Evidencia operativa: PENDIENTE DE PRIMER CICLO
Incumplimiento activo: NO EVIDENCIADO

La distinción que evita falsos diagnósticos. Una falta de historial no es una ejecución incompleta ni un incumplimiento. Confundirlos convierte una auditoría honesta en una acusación sin pruebas.

13

Operaciones peligrosas y recuperación

La referencia de recuperación solo se abre cuando alguien pide explícitamente recuperar, sobrescribir, borrar o reescribir historial. Y entonces cambia el estándar de la confirmación.

Autorización específica, no genérica

Hay que exponer los datos o la historia que podrían perderse, el alcance local o remoto, las alternativas seguras y el comando exacto. Se exige una confirmación que autorice ese comando concreto. Una aprobación genérica no sirve.

Orden de recuperación

  1. Inspeccionar estado, historial y reflog.
  2. Identificar los commits recuperables y preservar la evidencia.
  3. Preferir revertir o crear un commit correctivo.
  4. Usar reset destructivo, clean, force push o borrado solo cuando el usuario acepte expresamente sus consecuencias.

Y una regla de ejecución que no admite excepciones: no se encadenan comandos destructivos. Se verifica después de cada comando autorizado.

Por qué no se encadenan. Porque un destructivo que falla a medias es el peor estado posible: ni lo de antes ni lo de después, y sin saber dónde quedó. Encadenar convierte un error recuperable en una reconstrucción manual.

Preguntas cortas

Las dudas que aparecen en la primera sesión, con la respuesta directa.

¿Tengo que aprobar cada comando?

No. Apruebas un commit o un plan que enumera las etapas y su resultado esperado. Pero el commit nunca se ejecuta sin esa confirmación, y si el estado cambia, hay un conflicto o el resultado se desvía, se vuelve a preguntar.

Estoy en main y el cambio es pequeño. ¿Puedo commitear?

Sí, si la tarea es pequeña y de riesgo contenido: se preparan rutas enumeradas, se muestra el diff, se propone el mensaje en inglés y se pide confirmación. No hace falta una excepción documentada. Si la tarea es normal o compleja, se propone una rama corta.

¿En qué idioma va el mensaje de commit?

En inglés: nombre y descripción con el formato Conventional Commits, por ejemplo fix(cli): reject empty paths. El resto del proyecto sigue el idioma que le corresponda.

¿La skill aplica Git Flow a cualquier repositorio?

No. El modelo por defecto es main con ramas cortas y sin develop. Git Flow se aplica solo si el repositorio lo declara; si declara otro modelo, se conserva; si la evidencia es contradictoria, se exponen los hechos y se pide una decisión.

¿Por qué no puedo usar git add .?

Porque prepara todo lo que haya, incluido lo que no forma parte del encargo: archivos temporales, logs, cambios de otro. Se preparan rutas enumeradas, y si de verdad todo pertenece junto, el plan debe explicar por qué.

He integrado la feature. ¿Borro la rama?

Se propone, se informa del nombre y del comando git branch -d, y se pide confirmación. Si no la hay, la rama se queda. Una rama con trabajo no integrado, o una remota, no se borra sin autorización específica.

¿Y el push?

Requiere confirmación propia, aunque el commit ya esté confirmado y hecho. Un commit aprobado no autoriza a publicarlo, y una rama nueva tampoco se sube sola.

Hay un conflicto. ¿Lo resuelvo y sigo?

No sin un plan nuevo. Primero se informa de los archivos afectados y se ofrecen tres salidas: resolver archivos concretos, abortar o pausar. Resolver exige una decisión semántica por archivo y su propia confirmación.

¿Puedo hacer rebase de mi rama?

Solo si es privada y no está publicada. Una rama compartida o ya publicada no se rebasa ni se aplasta sin una regla documentada y aprobación explícita.

El repositorio solo tiene main. ¿Creo develop?

No. El modelo por defecto no usa develop: se trabaja en main para tareas pequeñas y en ramas cortas desde main para el resto. Crear develop requiere que el repositorio lo declare.

Me equivoqué con un commit. ¿reset --hard?

Primero se inspecciona estado, historial y reflog, y se prefiere revertir o un commit correctivo. Un reset destructivo exige autorización para ese comando concreto, con las consecuencias expuestas, y se verifica antes de cualquier paso siguiente.

¿Por qué el resultado dice NO VERIFICADO y no INCOMPLETO?

Porque son cosas distintas. INCOMPLETO significa que una condición obligatoria falló o no se ejecutó; NO VERIFICADO significa que no hay evidencia suficiente para afirmar nada. La skill prefiere el segundo antes que una conclusión sin pruebas.

He creado una rama. ¿Basta con eso?

No. Hay que verificar que el commit de base es descendiente de la base obligatoria y que no hay cambios no previstos en el árbol. Publicarla es otra operación que no ocurre automáticamente.

¿La skill sirve para un repositorio sin remoto?

Sí. Un flujo local no incumple nada por no tener remoto: las comprobaciones de ls-remote simplemente no aplican. Lo que no se hace es convertir esa ausencia en un incumplimiento inventado.

Resultado final

Todo cierre usa la misma forma. Si no se puede rellenar un campo con evidencia, ese es el hallazgo.

## Resultado verificado
- Estado:
- Tamaño de la tarea:
- Operación realizada:
- Evidencia Git:
- Commit: creado / no creado / pendiente de autorización
- Rama de trabajo: borrada / conservada / no aplicaba
- Push: realizado / no realizado / pendiente de autorización
- Validaciones:
- Tipo de resultado: EJECUCIÓN | AUDITORÍA
- Flujo ejecutado: COMPLETO | INCOMPLETO | NO VERIFICADO | NO APLICA
- Política y evidencia operativa: [usar estados de auditoría cuando corresponda]
- Diferencias respecto al plan:

Cómo se lee

CampoQué admite
Tamaño de la tareaPequeña, normal o compleja, con el motivo que la clasificó.
Commitcreado, no creado o pendiente de autorización. Los cambios preparados y sin commitear son un resultado válido.
Rama de trabajoborrada, conservada o no aplicaba. Si se conserva, se dice por qué.
Pushrealizado, no realizado o pendiente de autorización.
Tipo de resultadoEJECUCIÓN si se hizo algo; AUDITORÍA si solo se inspeccionó.
Flujo ejecutadoCOMPLETO, INCOMPLETO, NO VERIFICADO o NO APLICA.
Política y evidencia operativaLos estados de auditoría cuando el encargo no ejecutó un ciclo: política, estructura, evidencia operativa e incumplimiento activo.
Diferencias respecto al planLo que no coincidió. Si no hay diferencias, se dice; no se omite el campo.

El valor de este formato. Obliga a separar lo que se hizo de lo que se probó, y a distinguir una ejecución de una auditoría. Un informe que no puede rellenar «Evidencia Git» está describiendo una intención, y las intenciones no se firman.
