JavaScript que falla en la primera línea

La skill javascript-idiomatic-style escribe y revisa JavaScript vanilla para navegador y Node. Declara los dos baselines del motor antes de elegir sintaxis, prefiere la construcción que rechaza a la que convierte y deja una sola pieza que sabe en qué plataforma corre. El navegador o Node ejecutan; el diff, después.

Qué hace

Reduce el coste de leer y cambiar JavaScript sin tipos, sin framework y sin build. El código se escribe para dos objetivos posibles y el fallo se coloca donde se ve.

SituaciónQué hace la skill
Hay que escribir JavaScript nuevo para navegador, para Node o para ambos.Lee engines, browserslist y la convención; fija la intersección antes de escribir.
Una comparación o un valor por defecto se comporta raro.Sustituye == por === y || por ??, y explica la excepción == null.
Un módulo debe correr en el navegador y en Node.Separa lo compartido y nombra un adaptador; el dominio no conoce la plataforma.
Un flujo asíncrono deja rechazos sin observar o no se puede cancelar.Exige un consumidor del rechazo y propaga AbortSignal hasta la operación real.
Se construye interfaz con datos del usuario.Usa nodos y textContent; innerHTML con dato externo queda prohibido.
Se escribe un script o una CLI de Node sin dependencias.Usa node: builtins, parseArgs, stdout/stderr y process.exitCode.
Una regla de la skill choca con una convención escrita.Prevalece la convención del proyecto cuando no contradice al lenguaje.

Lo que no hace. No escribe ni ejecuta pruebas, no valida datos en runtime con una librería y no decide CSS ni calidad visual. Las pruebas y la puerta son de javascript-testing-and-verification; la interfaz visual, de web-interface-visual-design.

3

Cómo se usa

Seis pasos. El primero y el último son de lectura; los de en medio fijan el baseline, modelan, escriben y comprueban.

paso 1Inspeccionar

package.json, engines, browserslist, .nvmrc, runner, linter y vecinos. Comprueba la sintaxis de partida con node --check.

paso 2Fijar baseline y reparto

Baseline de cada objetivo, intersección, módulos compartidos y el adaptador de cada frontera.

paso 3Modelar datos y estados

Estados que no coexisten se separan; identificadores, cantidades y texto libre se nombran distinto.

paso 4Escribir

Contratos antes que cuerpos, guardas primero y la referencia del objetivo: lenguaje, asincronía, navegador o Node.

paso 5Verificar

node --check, el linter del proyecto y la ejecución real con los argumentos y variables del caso.

paso 6Revisar el diff

var, ==, innerHTML, eval, process.exit( y supresiones nuevas. Cierra con el bloque de resultado.

¿Qué es un baseline aquí?

El motor más antiguo que el proyecto promete soportar, por cada objetivo: el navegador que declara browserslist y la versión de Node que declara engines o el CI. Una edición ECMAScript no lo sustituye: la feature se comprueba contra el motor concreto.

¿Puedo usar || para un valor por defecto?

Solo si 0, "" y false significan de verdad «no hay valor». En una configuración, un contador o un texto opcional, se usa ??.

¿Y si el proyecto usa un bundler?

Se respeta. El baseline del código fuente pasa a ser el target del bundler; la skill no elimina el build para «volver a vanilla».

¿Cómo se comparte código entre navegador y Node?

Solo la parte que cabe en la intersección de los dos baselines. Lo que necesita document o node:fs vive detrás de un adaptador con nombre, y el dominio no lo conoce.

¿La skill ejecuta las pruebas?

No. Comprueba sintaxis, linter y ejecución real. Las pruebas y la puerta determinista pertenecen a javascript-testing-and-verification.

¿Se puede usar con un framework?

El lenguaje y los módulos sí; el componente no. React, Vue, Svelte y Angular quedan fuera del contrato de esta skill.

6

Preguntas cortas

Lo que se pregunta antes de usar la skill por primera vez.

¿Es una guía de estilo propia?

No. Ordena las decisiones del lenguaje para que el código se lea y falle pronto. Donde el proyecto ya tiene una regla escrita, manda la del proyecto.

¿Hay que migrar a ESM?

No dentro de un cambio funcional. La migración cambia type, extensiones y resolución; se propone aparte, con su coste.

¿Se pueden añadir dependencias?

Solo con justificación: primero el lenguaje y la plataforma. Un script que el navegador ejecuta tal cual no necesita un bundler.

¿Qué pasa si el navegador no soporta una feature?

Se sustituye por la alternativa que sí existe en el motor más antiguo del baseline. Si la alternativa exige una dependencia, es una propuesta, no un cambio de paso.

¿La skill arregla la deuda que encuentra?

No la esconde en el mismo diff. Si la corrección amplía el cambio, se termina la tarea actual y se registra la deuda con su motivo.

¿Cómo se relaciona con las skills de TypeScript?

Son excluyentes por archivo: .ts y .tsx van a las skills de TypeScript; .js, .mjs y .cjs sin tipos, a esta.
