Errores con significado, procesos con final

La skill go-errors-and-lifecycle trata el error como un valor con contrato: lo clasifica, lo envuelve con contexto, lo inspecciona con errors.Is y errors.As y lo traduce a un código de salida y a un mensaje machine-readable en un único punto. Después cierra el proceso: context, cancelación, timeouts, señales, concurrencia con propietario y recursos liberados en orden inverso.

Qué hace

Convierte cada fallo en una decisión para el llamador y cada proceso en algo que termina bien por cualquiera de sus salidas: éxito, error, cancelación, timeout o cierre del propietario.

SituaciónQué hace la skill
Hay que definir o revisar errores.Los clasifica por quién puede actuar y elige centinela, tipo propio, error opaco o defecto de programación.
Un fallo tiene que llegar al agente con un código estable.Mapea el error a code, mensaje accionable y código de salida en un único punto.
Hay que añadir context, cancelación o timeouts.Propaga el contexto por toda operación de I/O, deriva el timeout en su frontera y distingue cancelación de timeout.
Hay que manejar señales.Instala signal.NotifyContext en main, deja de aceptar trabajo, cancela y espera con un límite.
Hay que introducir concurrencia.Exige propietario, condición de terminación, propagación y espera para cada goroutine; si falta una, no se lanza.
El proceso tiene que cerrar sin fugas.Ordena el cierre en orden inverso a la apertura, propaga el primer error y declara qué quedó sin cerrar.

Lo que no hace. No fija el contrato de la CLI, no impone estilo general ni escribe las pruebas. La CLI define los códigos; esta skill los respeta y centraliza su traducción.

3

Cómo se usa

Ocho pasos: cuatro para el error, tres para el ciclo de vida y uno para demostrarlo.

paso 1Inventariar

Qué operaciones fallan, quién actúa y dónde están las fronteras: dominio, CLI, red, disco y proceso.

paso 2Definir la taxonomía

Centinelas para condiciones estables, tipos para datos inspeccionables, errores opacos para depuración y un code en la frontera.

paso 3Implementar el flujo

Comprobar de inmediato, añadir contexto que falte y conservar la causa con %w.

paso 4Traducir en la frontera

Un solo punto para code, mensaje, código de salida y sobre JSON; sin secretos ni rutas internas.

paso 5Propagar el contexto

ctx en toda operación de I/O y espera; timeout en su frontera; cancelación distinta de timeout.

paso 6Justificar la concurrencia

Propietario, terminación, propagación y espera por goroutine. errgroup para tareas relacionadas.

paso 7Cerrar el proceso

Señal, cancelación, espera con deadline, cierre inverso y salida con 3 o 1 según la causa.

paso 8Verificar

Errores con errors.Is/errors.As, cancelación sin goroutines ni temporales, vet y -race.

¿Centinela, tipo o error opaco?

Centinela cuando el llamador compara la condición con errors.Is; tipo propio cuando necesita datos con errors.As; opaco cuando solo hace falta contexto de depuración. El mensaje no es la identidad del error.

¿%w o %v?

%w cuando la causa debe seguir siendo inspeccionable; %v solo en una frontera donde no se quiera exponer el interior. El verbo va al final del formato y no se usa más de un %w por fmt.Errorf.

¿Cancelación y timeout son lo mismo?

No. La cancelación la decidió el llamador; el timeout lo impuso un límite. Tienen distinto code, distinto mensaje y distinto código de salida: 3 frente a 1.

¿Cuándo hay que usar errgroup?

Cuando varias tareas relacionadas deben cancelarse entre sí y propagar el primer error. sync.WaitGroup solo sirve para esperar, sin errores que propagar. Un canal transfiere propiedad; un mutex protege estado compartido.

¿Qué pasa con un segundo SIGINT?

Puede forzar la salida si el programa lo implementa, y entonces se documenta. Lo que no se hace es bloquear indefinidamente el cierre por dejar recursos abiertos.

¿Puedo recuperar un panic y devolverlo como error?

Solo en un límite conocido y si representa un fallo de operación. Un panic que oculta un defecto de programación no se convierte en error: se corrige o se declara.

6

Preguntas cortas

Lo que se pregunta antes de usar la skill por primera vez.

¿Un error se registra o se devuelve?

Se elige una vez. Se devuelve con contexto o se registra en la frontera, nunca ambas, para que el mismo fallo no aparezca duplicado y con mensajes distintos.

¿Por qué no comparar textos de error?

Porque el texto es presentación y puede cambiar sin cambiar la condición. La lógica usa errors.Is y errors.As; el texto se prueba solo donde es el contrato visible.

¿Se puede guardar el contexto en un struct?

No. context.Context es el primer parámetro de las funciones que hacen I/O, esperan o se cancelan. No se guarda, no se usa para parámetros opcionales y no se sustituye por un tipo propio.

¿Toda función debe aceptar contexto?

Solo las que hacen trabajo cancelable: I/O, espera o llamadas externas. Una función pura no necesita contexto y añadirlo sin motivo ensucia la firma.

¿Cómo se declara el cierre incompleto?

No se promete atomicidad que el código no garantiza. Si la cancelación deja estado parcial, se declara si la operación es atómica o reanudable y cómo se limpia.

¿Qué hago si el proyecto ya tiene su envelope de errores?

Se respeta y se mapea a él. La compatibilidad con el contrato publicado manda; esta skill no impone su sobre por encima.

8

Verificación

Los errores, la cancelación y los recursos se prueban con las herramientas del proyecto; sin esa evidencia no hay cierre.

gofmt -l .
go build ./...
go test ./...
go test -race ./...
go vet ./...
python3 scripts/check-repo.py
CódigoSignificado
0Formato, compilación, pruebas, carrera y vet sin hallazgos.
distinto de 0Algún comando falla; se corrige por categoría antes de cerrar.

La puerta no demuestra que cada error tenga contexto útil: eso se lee en el diff. Un error esperado se devuelve; panic solo para invariantes imposibles.
