Python que declara lo que acepta

La skill python-idiomatic-style posee el lenguaje, los tipos, la estructura del proyecto, las dependencias, el empaquetado y la forma de una CLI. Modela los estados con dataclasses y uniones, anota la API pública, propaga excepciones con causa y deja el proyecto en un único pyproject.toml.

Qué hace

Convierte una preferencia de estilo en un contrato comprobable. El tipo, el error y el recurso se declaran antes; el defecto no llega a producción.

SituaciónQué hace la skill
Hay que modelar datos y estados.Elige dataclass, Enum, TypedDict o Protocol según la tabla de decisión, no por costumbre.
La API pública no dice qué acepta.Anota parámetros y retorno, justifica cada Any y comprueba con mypy o pyright.
Un fallo se pierde en silencio.Define la jerarquía de excepciones, conserva la causa con raise ... from y prohíbe except Exception: pass.
Ficheros, conexiones o locks quedan abiertos.Exige with o un @contextmanager; envuelve el recurso que no lo trae.
El proyecto no tiene una fuente de verdad.Ordena pyproject.toml, layout src/, dependencias y build sin añadir capas.
Hay que construir una CLI.Fija comandos, salida separada, códigos de salida, --dry-run y modo no interactivo.
Entra dato de una frontera no confiable.Lo señala y lo remite a python-testing-and-verification: el tipo no valida en runtime.

Lo que no hace. No escribe pruebas ni ejecuta la puerta; no decide la validación en runtime; no impone un framework web ni una biblioteca de terceros. Esa materia pertenece a python-testing-and-verification, security-engineering y las skills del lenguaje del adaptador.

3

Cómo se usa

Seis pasos. Se inspecciona antes de escribir, se modelan los estados una vez y el cierre se demuestra con herramientas, no con adjetivos.

paso 1Inspeccionar

pyproject.toml, lockfile, versión de Python, layout, linter y comprobador. El estado de partida se ejecuta antes de tocarlo.

paso 2Modelar

Una frase por entidad y por estado. Identificadores, cantidades y contenido libre se separan; el error base se define antes del camino feliz.

paso 3Escribir

Firmas públicas antes de los cuerpos, guardas primero, y la referencia de lenguaje o de tipos cuando la decisión no es evidente.

paso 4Proyecto

Metadatos, layout y dependencias en un solo sitio. Una dependencia nueva exige su alternativa descartada.

paso 5CLI

Argumentos validados al entrar, stdout separado de stderr, códigos acotados y confirmación para lo destructivo.

paso 6Comprobar el diff

ruff format --check, ruff check y el comprobador de tipos. Busca Any, type: ignore y dependencias nuevas.

¿Qué comprobador de tipos usa?

El que el proyecto ya tenga. La referencia de tipos escribe la configuración de mypy estricto y el equivalente de pyright, pero no impone la migración dentro de un cambio funcional.

¿Dataclass o diccionario?

dataclass cuando las claves son campos conocidos; dict solo cuando las claves son datos. Un JSON externo se describe con TypedDict y se valida en runtime en la otra skill.

¿Por qué src/?

Evita que las pruebas importen el paquete por accidente desde el directorio actual. Un script suelto no necesita paquete; un paquete pequeño y plano es válido si el build funciona.

¿Se añade Typer?

Solo si el proyecto ya lo usa o si la CLI necesita subcomandos y ayuda declarativa que justifiquen la dependencia. El contrato de salida y códigos no cambia.

¿Qué pasa con la validación del dato externo?

Queda fuera de esta skill. La anotación no rechaza nada; la comprobación y sus pruebas pertenecen a python-testing-and-verification.

¿Se permite float para dinero?

No. Decimal con una política de redondeo declarada, o enteros de la menor denominación.

6

Preguntas cortas

Lo que se pregunta antes de usar la skill por primera vez.

¿Impone uv?

Es la elección por defecto cuando no hay otra declarada. pip con requirements.txt se respeta si ya existe; lo que no se acepta es un segundo gestor y un segundo lockfile.

¿Es obligatorio strict?

Es el punto de partida para un proyecto nuevo. En uno existente, activarlo es una migración aparte con su coste medido.

¿Se permite except Exception?

Solo con una razón escrita. except Exception: pass no se acepta: convierte un defecto en un resultado válido.

¿Qué se hace con una dependencia sin tipos?

Se aísla el Any en un adaptador y se documenta el límite; no se extiende por el dominio ni se parchea node_modules o el entorno.

¿La skill publica el paquete?

Prepara el build y comprueba el artefacto. Publicar es una operación aparte, con su propia confirmación.

¿Y la seguridad?

El modelo de amenazas, los secretos y la revisión de dependencias pertenecen a security-engineering; esta skill no los sustituye.

Verificación

La sintaxis, el formato, el lint y la puerta del repositorio se ejecutan; una herramienta ausente se declara.

python3 -m compileall -q .
ruff format --check .
ruff check .
python3 scripts/check-repo.py
CódigoSignificado
0Sintaxis, formato, lint y puerta sin hallazgos.
distinto de 0Algún comando falla o una herramienta no está instalada; se declara antes de cerrar.

compileall no ejecuta el código. ruff y el comprobador de tipos son del proyecto: si no están instalados, el hueco se informa, no se omite.
