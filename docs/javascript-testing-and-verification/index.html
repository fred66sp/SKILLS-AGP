Prueba lo que se ejecuta, no lo que imaginas

La skill javascript-testing-and-verification elige la capa más pequeña que demuestra el comportamiento: node:test para lógica y proceso, una página de navegador para el DOM. Sustituye red, reloj y aleatoriedad por dobles, y cierra con una puerta que comprueba sintaxis y ejecuta las pruebas del proyecto sin añadir un framework.

Qué hace

Convierte una sospecha en evidencia ejecutada: elige la capa, escribe el caso que falla por la causa correcta y deja una puerta repetible en otra máquina.

SituaciónQué hace la skill
Hay que probar lógica, cálculos o transformaciones.Escribe casos con node:test y node:assert/strict, junto al módulo, sin dependencias.
El comportamiento vive en el DOM.Usa una página de pruebas con nodos reales: texto, estado, eventos y foco.
La operación depende de la red, el reloj o el azar.Sustituye la frontera por un doble controlado; espera eventos, nunca milisegundos.
El contrato es una CLI de Node.Ejecuta el proceso con argv, env y stdin controlados y comprueba los tres canales por separado.
Aparece un defecto.Primero la prueba que falla por su causa; después la corrección. La prueba queda como regresión.
Hay que declarar el cambio terminado.Ejecuta verify-js.py y rellena el informe con lo ejecutado y lo que no.
El proyecto ya tiene Vitest, Jest o un script test.Se usa ese runner y esa puerta; la skill no lo sustituye.

Lo que no hace. No escribe la implementación, no impone estilo ni decide la forma del DOM. El lenguaje, los módulos y el runtime son de javascript-idiomatic-style; la calidad visual, de web-interface-visual-design.

3

Cómo se usa

Seis pasos. El riesgo se mapea antes de escribir, la capa se elige una vez y el cierre se demuestra con comandos.

paso 1Mapear riesgos

Qué observa el usuario, dónde entra dato no confiable, qué se destruye o se filtra y qué cambia a menudo.

paso 2Elegir capa y runner

Función pura con node:test, DOM en navegador, proceso ejecutado. Si hay runner, ese manda.

paso 3Escribir el caso

Una razón para fallar, un mensaje legible y los límites que importan: vacío, cero, null, error de red, cancelación.

paso 4Aislar y estabilizar

Dobles de red, reloj y almacenamiento; espera de eventos; limpieza de temporales y listeners.

paso 5Ejecutar la puerta

verify-js.py con --test y --lint cuando existan. La puerta no sustituye al runner del proyecto.

paso 6Cerrar con evidencia

Informe con comandos, resultado y lo no verificado. Sin adjetivos.

¿Necesito instalar un framework de pruebas?

No. node --test ejecuta archivos *.test.js con node:test y node:assert/strict sin dependencias. El navegador ya es el entorno del DOM.

¿Y si el proyecto usa Vitest o Jest?

Se usa el que tenga. La puerta detecta el script test del proyecto y lo ejecuta con el gestor declarado; no descarga otro runner.

¿Cómo se prueba el DOM?

Con la página de assets/test-runner.html, que registra casos y los ejecuta al cargar, o con el entorno que el proyecto ya tenga. No se añade un DOM simulado para un módulo pequeño.

¿Qué comprueba exactamente verify-js.py?

Sintaxis con node --check en todos los .js, .mjs y .cjs del proyecto; con --test, el script test o node --test; con --lint, el script del proyecto. Informa de la versión de Node frente a engines.

¿La puerta falla si no hay pruebas?

Solo si se pide --test y no hay script ni archivos de prueba. Sin --test, la ausencia de pruebas no es un fallo de sintaxis.

¿La cobertura es un objetivo?

Es una señal. Un umbral se acepta si ya existía; no se impone dentro de un cambio funcional ni se escriben pruebas triviales para subirlo.

El agente lee SKILL.md al activarse, abre la referencia de la capa elegida y ejecuta la puerta en lugar de reescribirla.

│   ├── verify-js.py              # puerta determinista
│   └── test-verify-js.py         # pruebas de la puerta
└── agents/

FicheroCuándo lo abre el agente
SKILL.mdSiempre, al disparar la skill.
references/test-layers.mdPasos 1 y 2, al mapear riesgos y elegir capa.
references/node-tests.mdPaso 3, cuando la capa sea node:test o un proceso.
references/browser-tests.mdPaso 3, cuando la capa sea el navegador.

6

Preguntas cortas

Lo que se pregunta antes de usar la skill por primera vez.

¿Sustituye a Vitest o Jest?

No. Si el proyecto ya los tiene, se usan. La skill aporta el criterio de capa, los dobles y la puerta; el runner es del proyecto.

¿Se puede probar DOM sin instalar nada?

Sí: una página que carga el código, el runner y los casos, abierta en el navegador. Demuestra comportamiento del DOM, no CSS ni accesibilidad completa.

¿Qué pasa con TypeScript?

Queda fuera: las pruebas de TypeScript y su typecheck pertenecen a typescript-testing-and-verification.

¿Cómo se prueba una CLI?

Ejecutando el proceso con process.execPath, argumentos, entorno y entrada controlados; se comprueban stdout, stderr y código de salida por separado.

¿Qué hago con una prueba inestable?

Se corrige o se elimina con motivo escrito. No se marca como omitida ni se le añade una espera mayor.

¿La puerta necesita package.json?

Solo para --test y --lint. La comprobación de sintaxis funciona en una carpeta de scripts sin paquete.

Verificación

La puerta y sus propias pruebas se ejecutan; lo que no se pudo verificar se declara con su motivo.

python3 src/javascript-testing-and-verification/scripts/verify-js.py --root . --test --lint
python3 src/javascript-testing-and-verification/scripts/test-verify-js.py
python3 scripts/check-repo.py
CódigoSignificado
0Todas las comprobaciones ejecutadas pasan.
1Alguna comprobación falla; se corrige por categoría, no se silencia.
2Uso inválido o una herramienta requerida no está disponible.

La puerta ejecuta el proyecto y solo debe usarse sobre código confiable o en un contenedor sin privilegios. No sustituye al runner del proyecto.
