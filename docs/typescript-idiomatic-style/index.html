TypeScript que no permite el estado imposible

La skill typescript-idiomatic-style escribe y revisa TypeScript type-first para librerías, servicios y CLIs. Modela primero los estados, usa unknown en las fronteras y reserva los genéricos, las project references y las dependencias para una necesidad demostrada. El compilador es la primera prueba; el diff, la segunda.

Qué hace

Reduce el coste de leer y cambiar TypeScript sin sacrificar seguridad de tipos, claridad ni capacidad de evolución. El sistema de tipos se usa para diseñar, no para satisfacer al compilador con as.

SituaciónQué hace la skill
Hay que escribir TypeScript nuevo en una librería, un servicio o una CLI.Lee tsconfig, versión y convención; modela los estados antes de escribir cuerpos.
Aparecen varios booleanos que se excluyen.Los sustituye por una unión discriminada con campo literal y comprobación never.
Un identificador de dominio se mezcla con texto libre.Lo modela con un tipo branded construido en un único módulo.
Hay que decidir genéricos, tipos calculados o satisfies.Exige dos usos reales o una relación entre entrada y salida; si no, escribe el tipo concreto.
Hay que resolver módulos, exports o project references.Mantiene el barrel solo para la API pública y añade referencias tras medir el build.
Hay que construir o revisar una CLI.Aplica defineCommand, isCancel, completion perezosa y códigos de salida 0/1/2.
Una regla de la skill choca con una convención escrita.Prevalece la convención del proyecto cuando no contradice al lenguaje.

Lo que no hace. No valida datos en runtime, no escribe pruebas ni ejecuta la puerta de CI. La frontera no confiable, las capas de prueba y la evidencia son de typescript-testing-and-verification.

3

Cómo se usa

Seis pasos. El primero y el último son de lectura; los de en medio modelan, escriben y comprueban.

paso 1Inspeccionar

package.json, tsconfig.json, versión de TypeScript, gestor y vecinos. Ejecuta el typecheck de partida.

paso 2Modelar los estados

Una frase por estado y por transición. Identificadores con brand; dato externo marcado como frontera.

paso 3Escribir tipos e implementación

Uniones, guards con value is T, firmas antes que cuerpos, satisfies en tablas y as const en constantes.

paso 4Resolver módulos y exports

Dominio separado del adaptador, sin ciclos, barrel solo para la API pública y exports explícito en librerías.

paso 5Construir la CLI, si la hay

defineCommand, subcomandos perezosos, isCancel tras cada prompt, salida separada y completion fuera del arranque.

paso 6Comprobar el diff

tsc --noEmit y lint. Busca any, as, enum y supresiones nuevas. Cierra con el bloque de resultado.

¿Cuándo se justifica un genérico?

Cuando hay al menos dos instancias reales o una relación entre parámetros y retorno. Un genérico de un solo uso es un tipo concreto disfrazado; se escribe el concreto y se explica qué lo haría merecer la abstracción.

¿Por qué no enum?

Porque genera código en runtime y complica el contrato con JavaScript. Un const object con as const y una unión derivada da los mismos valores sin esa carga.

¿Puedo usar as?

Solo cuando el valor ya cumple una invariante demostrada, de forma puntual y comentada. En una frontera externa, as no valida: se parsea con la skill de verificación.

¿Se activan las project references?

Cuando una medición del build demuestra el problema y la mejora. No son parte de la plantilla mínima ni se añaden por anticipación.

¿Qué pasa si el proyecto no usa strict?

No se activa dentro de un cambio funcional. Se propone la migración aparte, con su coste y sus errores esperados.

¿La skill ejecuta las pruebas?

No. Ejecuta el typecheck y el linter si existe. Las pruebas, la validación en runtime y la puerta completa pertenecen a typescript-testing-and-verification.

6

Preguntas cortas

Lo que se pregunta antes de usar la skill por primera vez.

¿Es una guía de estilo propia?

No. Ordena las decisiones del lenguaje para que los tipos y la CLI se mantengan legibles. Donde el proyecto ya tiene una regla escrita, manda la del proyecto.

¿Hay que migrar a strict?

No dentro de un cambio funcional. La migración se propone aparte, con el coste medido y las reglas que se puedan asumir: noUncheckedIndexedAccess, exactOptionalPropertyTypes, isolatedModules.

¿Monomrepo o un paquete?

Un paquete y un tsconfig hasta que el tamaño o el build demuestren lo contrario. Las project references se añaden con una medición, no como plantilla.

¿Qué CLI usa?

citty para los comandos y @clack/prompts para la interacción. Si el proyecto ya tiene otra, se respeta; no se añade un segundo parser.

¿Y los tipos de una dependencia rota?

Se aísla el any en un adaptador, con comentario y sin extenderlo por el dominio. No se parchea node_modules.

¿La skill arregla la deuda que encuentra?

No la esconde en el mismo diff. Si la corrección amplía el cambio, se termina la tarea actual y se registra la deuda con su motivo.
